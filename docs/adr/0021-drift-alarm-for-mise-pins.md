# ADR-0021: Bumping mise pins — manual, with a scheduled drift alarm

**Context:** `.mise.toml` (ADR-0010) pins seven tools — `node`, `pnpm`, `fnox`, `age`, `wrangler`, `actionlint`, `shellcheck` — and nothing bumped them. Dependabot (`.github/dependabot.yml`) covers npm and the Actions, but it has no `mise` ecosystem, so those pins were invisible to it and drifted silently: nothing noticed a pin falling behind until a stale tool broke CI or the local/CI parity ADR-0010 set out to guarantee. It had already happened — `fnox` was pinned at `1.25.1`, ten minor releases behind upstream.

**Options considered:**

- (a) **Renovate** — a native `mise` manager covering all seven tools, and able to take npm and the Actions off Dependabot too. Rejected: its PRs come from a GitHub App, not Dependabot, so GitHub's separate Dependabot secrets store does not apply to them and they receive the repository's Actions secrets — reintroducing exactly the production-credential exposure ADR-0020 closes. It also adds a third-party app to solve a problem a weekly check solves.
- (b) **A scheduled workflow that opens the bump PR itself.** Rejected: a PR created with a workflow's `GITHUB_TOKEN` does not trigger further workflows, so the bump would arrive with no CI signal at all — the failure mode of issue #45. Widening it to a PAT or App token to restore the signal puts a long-lived credential back in circulation for a chore.
- (c) **Manual bumps, plus a scheduled drift alarm.**

**Decision:** (c). `.github/workflows/toolchain-drift.yml` runs weekly on `master`, calls `mise outdated --local --bump --json`, and opens — or refreshes — a `toolchain-drift` issue listing every pin whose newest upstream release falls outside what the pin allows. When nothing is behind it closes the issue again. The run stays green: the alarm is the issue, not a red X, because a pin being behind is a judgement call and a major bump is a decision. The issue body is the checklist — bump the pin in `.mise.toml`, run `mise install`, re-run `pnpm install` if `node` or `pnpm` moved, verify with `pnpm turbo build test lint typecheck format:check`, then close the issue, which the next run reopens if anything is still behind.

`--bump` is what makes the signal mean "the pin is stale" rather than "this runner has an old install": it reports a tool only when a release exists _outside_ the pin's range. A ranged pin that already covers the newest release (`node = "26"` while 26.x is current) stays quiet, while an exact pin (`fnox = "1.25.1"`) speaks as soon as a newer release exists. Majors therefore always surface, and patch churn only surfaces for pins deliberately held exact. This is also why the workflow opens an issue rather than a pull request: ADR-0020's secret gating is about runs that install bumped code, and neither an issue nor a hand-authored bump PR is such a run.

Between the two mechanisms, Dependabot watches the ecosystems named in `.github/dependabot.yml` and the alarm watches `.mise.toml`. Two versions sit deliberately outside both, bumped by hand when their meaning moves rather than when upstream releases: `packageManager`, the source of truth for the exact pnpm that runs, and `engines.node`, the floor a consumer of these packages needs.

A third sits outside both and cannot sit inside them: the browser `apps/web`'s component tests run in. CI drives the runner image's preinstalled Chrome (`channel: "chrome"` when `CI` is set), because the image already carries the browser and its OS dependencies — the browser-cache restore and the `install-deps` step this removes cost 5 s and 18 s in the measured baseline run — while local runs keep the Chromium `pnpm-lock.yaml` pins, and the test command is identical in both. Nothing watches the CI browser and nothing can; it moves when GitHub's runner image moves. The component tests assert rendering behaviour, not a browser build, so the drift is accepted rather than tracked (PR #141).

Three `.mise.toml` entries have a counterpart in `package.json`, and the duplication is deliberate once spelled out:

- `pnpm = "12"` vs `"packageManager": "pnpm@12.4.1"`. Different jobs: the mise range guarantees a pnpm 12.x on `PATH` so `pnpm` runs at all, while `packageManager` is the exact version that runs — pnpm's default `pmOnFail: download` makes the declared version authoritative, downloading and running 12.4.1 rather than failing when `PATH` holds a different 12.x.
- `node = "26"` vs `"engines": { "node": ">=24" }`. Different claims, not a conflict: `engines` is the floor a consumer needs, the mise pin is what the repo builds and deploys on. Move `engines` only when the floor genuinely moves.
- `wrangler = "4"` vs `"wrangler": "^4.131.2"` in `apps/*`. Reconciled by this decision. The pin used to be an exact `4.131.1`, which both overstated it and made the alarm noisy: inside a package, `pnpm run` puts `apps/*/node_modules/.bin` ahead of the mise shim, so the devDependency is the wrangler that actually deploys, and the exact pin only notified the team of its own patch churn every week. As a range it matches the devDependency's `^4.131.2` — both mean "the 4.x line" — Dependabot maintains the devDependency, and the alarm speaks only when 5.x arrives.

**Trade-offs:** Manual bumps mean a pin stays behind until someone acts on the issue; the alarm turns that from an oversight into a decision, but it does not do the work. A weekly check is silence when it is quiet and one issue when it is not, and it closes its own issue when the drift clears, so an open `toolchain-drift` issue always means something is behind _right now_ rather than "was, once" — which keeps the alarm worth reading. The comparison is against the pin's range, so it will not report that a ranged pin's newest in-range release moved; that is safe because a ranged pin resolves to the newest match at install time, but it means ADR-0010's "identical versions" promise still rests on pins being ranges rather than on a lock — this repo does not use `mise.lock`, so `node = "26"` can resolve to different 26.x builds on different days, and adding one would close that last gap. The `wrangler` pin also moves from a fixed release to a floating `4.x` as part of the reconciliation above; the devDependency already floated, so the two now move together instead of apart. Renovate stays the option to revisit if manual bumps become the bottleneck, but it should be revisited together with ADR-0020's gating, not around it.
