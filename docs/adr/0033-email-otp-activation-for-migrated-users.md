# ADR-0033: Migrated users activate by email OTP; legacy passwords are not carried

**Context:** Legacy `master.users.password` holds `$2y$12$` bcrypt hashes (BCRYPT_ROUNDS=12; every row in the only data we can see). Better Auth verifies scrypt and exposes `emailAndPassword.password.verify`, so a lazy migration was possible — verify bcrypt, rehash to scrypt on a user's first login. The alternative was to carry no passwords at all and have every migrated user activate once; cutover is also the moment users learn the platform has moved.

**Options considered:**

- **Lazy migration (verify bcrypt, rehash on login).** No cutover comms needed, but every migrated user's first login pays bcrypt (~300 ms CPU at cost 12 on Workers, measured in Miniflare) on top of scrypt's ~130–175 ms (ADR-0012), and legacy hashes live on through the migration window.
- **Keep bcrypt verification permanently.** No user friction, but pins a legacy hash format into production and keeps the Workers CPU cost forever.
- **Force a reset by emailed link at cutover.** Familiar click-through, but the link points at the API origin where a session cookie never reaches `apps/web` — the reason ADR-0018 forbids auto-signin-after-verification — and bulk-sent links with long TTLs are long-lived credentials sitting in inboxes.
- **Carry no credentials; activation by email OTP.** Chosen.

**Decision:** The identity transform imports each legacy account with no credential row; `master.users.password` is dropped and no bcrypt hash enters Better Auth. First access is an activation: the login page sends a one-time code (`emailOTP` plugin, `disableSignUp: true`, 5-minute expiry), and the same screen takes the code plus a new password (`emailOTP.resetPassword`, which creates the missing credential). Migrated users import as `emailVerified: true` — they are admin-provisioned and every row we can see carries `email_verified_at` — so the password sign-in that follows is not blocked by `requireEmailVerification`. Phone is not a channel: Better Auth's phone plugin ships no SMS vendor and legacy phone data is not identity-grade. The awareness job is done by an announcement email carrying no secret, sent on demand rather than bulk.

**Trade-offs:** Every migrated user needs a working inbox to get in, so cutover-day support moves from "nobody" to "anyone whose email bounces" — mitigated by the admin fallback (an admin sets a password through #6's user detail, or triggers a fresh activation) and by activating the super-admins first. In exchange no legacy hash format reaches production, the first login cannot fail on a Workers CPU budget, and the activation email doubles as the platform announcement.

**Consequences:** #7 builds and fixture-tests the transform, wires the OTP transport through `apps/api/src/email.ts` (ADR-0017; previews log instead of send, #121), and owns the sign-in gate that reads the business record. The cutover runbook (#17) activates super-admins first and records the admin fallback; the rehearsal (#18) exercises activation end to end.

**Amendment (2026-10-04, #254):** `/activate` no longer takes the code and the new password on the same screen. It has three steps on one route: the email, then the code, then the new password. Verify checks the code with `check-verification-otp` (type `forget-password`). That check counts a wrong try toward the code's 3 attempts but does not use the code up, so the password step can still spend it with `emailOTP.resetPassword`. Between the two, the email and checked code wait in an httpOnly, `SameSite=Strict`, `Secure` cookie scoped to `/activate`, lasting 5 minutes (`apps/web/src/lib/server/checked-code.ts`). The page's load picks the password step from it, and without it the password step cannot be reached. It is cleared on success, on requesting a code and on "Use a different email". An expired, used-up or wrong code sends the password step back to the code step with the email kept. An unregistered email has no code to check, so Verify answers it `INVALID_OTP`, as it does a wrong code (#232).

**Trade-offs of the amendment:** the code now sits in a browser cookie for up to 5 minutes. It is the user's own code and Better Auth checks it again when the password is set, so a cookie edited by hand gets no further than a form could. The access seam forwards the browser's cookies to apps/api (ADR-0034's #226 amendment), so the cookie also reaches apps/api on activate actions, alongside the same code the password request already sends; Better Auth ignores it. Better Auth replies `OTP_EXPIRED` and `TOO_MANY_ATTEMPTS` only for a registered email, and checks a registered email's wrong code more slowly than an unregistered email. That was already true of `reset-password` and is not changed here; a follow-up issue owns it.

**Amendment (2026-10-04, #271):** public OTP requests now retain an unsent, high-entropy decoy for an unknown email. Both kinds of email take the same database path on issuance and on a wrong, expired or exhausted code. Better Auth still owns checking and atomic redemption; its useful `OTP_EXPIRED` and `TOO_MANY_ATTEMPTS` replies are preserved. The deprecated reset-request alias and generic OTP-send endpoint also use this issuance path, so calling apps/api directly cannot bypass it. The generic endpoint keeps decoys for its other public OTP types as well. Codes and decoys are stored as SHA-256 hashes through one hasher shared with the plugin. Native rate limits, five-minute expiry, background email delivery, and disabled public sign-up are retained.

**Trade-offs:** unknown emails occupy verification rows until native cleanup removes them. Issuance deletes the previous code before storing the replacement for both kinds of email, adding work to the registered request but removing the timing difference caused by unknown-only deletion. Codes issued before deployment used plaintext storage and need to be resent after this change; no password or session migration is required. The measured Neon before/after timings and limitations are in [the OTP enumeration experiment](../research/otp-enumeration-timing.md).

**Amendment (2026-10-12, #405):** a Trashed user (ADR-0055) is an unknown email to the OTP endpoints. Issuance looks the business record up for every email (a random id for an unknown one, so the work is equal), sends nothing and stores a decoy for a Trashed user. A `before` hook on check, reset, email-verify and OTP sign-in does the same lookup and, for a Trashed user, swaps the stored secret for a decoy, keeping the attempt count and expiry, so a code issued before the delete fails as an unknown email's does and `reset-password` writes no credential. Any other email aims the same reads and write at an identifier with no row.
