# ADR-0030: Fork PRs skip Preview and Cleanup

**Context:** GitHub passes no repository secrets to a `pull_request`-triggered workflow run from a forked repository (`GITHUB_TOKEN` excepted, per GitHub's documented behaviour), so a code-relevant fork PR started `preview.yml`'s `preview` job and failed at `Resolve preview identifiers` on an empty `CLOUDFLARE_API_TOKEN`, and `cleanup.yml`'s `cleanup` job failed at its first secret-dependent step when that PR closed (issue #149). Nothing leaked and neither job was ever unsound — the runs just turned red for a reason unrelated to the change, which ADR-0020 already names as worse than no check. Both jobs need Neon and Cloudflare credentials, so neither can be made secret-free the way `ci.yml`'s Dependabot step is.

**Options considered:**

- (a) Keep plain `pull_request` and guard both jobs on the head repository: the `preview` job in `preview.yml` and the `cleanup` job in `cleanup.yml` run only when `github.event.pull_request.head.repo.full_name == github.repository`.
- (b) Switch the triggers to `pull_request_target`, which runs the base repository's workflow file with the repository's secrets available. Rejected: the fork's code is still built and deployed — that is what the preview is for — so this is the credential exposure ADR-0020 rejects, with the added hazard that the fork's own workflow edits are ignored while its code is not.
- (c) Drop the fork guard and accept red runs. Rejected: that is the status quo the issue exists to fix.

**Decision:** (a). Plain `pull_request` stays the trigger — the documented-safe shape — and each of the two secret-bearing jobs gains `github.event.pull_request.head.repo.full_name == github.repository` as a final conjunct on its `if:`. A guard term rather than a trigger change keeps the existing Dependabot skip and the `changes` gate untouched, and a fork PR then concludes `skipped`, which GitHub treats as a success for a required check, exactly as the Dependabot skip does (ADR-0020). Same-repo PRs evaluate the added term to `true`, so their full path is unchanged. A fork PR never creates a Neon branch or a Pages deployment, so skipping `cleanup.yml` for it leaves nothing behind — the same reasoning that already lets `cleanup.yml` skip Dependabot PRs.

**Trade-offs:** A fork PR gets no preview environment, so a contribution from outside is not exercised against a live stack before review. Accepted: the alternative is `pull_request_target`, which hands production-capable credentials to code nobody has reviewed yet, and a maintainer who wants the full path can push the fork's commits to a same-repo branch. The scope here is deliberately the two preview jobs: a fork PR's `ci.yml` run still reaches the fnox-wrapped `Verify` step and fails on the missing `FNOX_AGE_KEY`, so whether fork PRs should get a secret-free CI path in ADR-0020's shape is left open.
