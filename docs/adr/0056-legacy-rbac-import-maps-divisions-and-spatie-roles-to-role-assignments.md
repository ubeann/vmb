# ADR-0056: The legacy RBAC import turns divisions and Spatie roles into role assignments

**Context:** The new schema has no `master.users.division_id` (D-013): a user's division is the division of the roles they hold, and a role is scoped to one division or to all (ADR-0045). A legacy snapshot still carries `users.division_id`, `master.roles`, `master.permissions` and the three `spatie.*` pivots, and the import leaves all of them behind (D-003), so a rehearsal lands users with no roles and nobody can open a Master screen. #311 adds the RBAC half of the transform. Shaping it on 2026-10-16 against the legacy source (`ubeann/vmb-warehouse`, branches `development` and `revamp`) settled the questions below. The facts that drove them: the deployed app seeds four roles (Super Admin, a system role; Manager Finance; and two generic roles, Manager Division and Staff, each used in several divisions); every user pairs one role with one division; revamp's target shape is Super Admin and Executive unscoped, then `Manager - <Division>` and `Staff - <Division>` for Finance, Operations and Trucking; legacy permission names are already `resource.action` in the catalogue's spelling; and nothing ever wrote a direct user-to-permission grant.

**Options considered:**

- **Carry every role unscoped and only the assignments.** Nothing is split, but every user's division is lost, which D-013 forbids.
- **Split every non-system role per division.** Deterministic, but it also splits a role that only one division ever used, changing its id and name for nothing.
- **Split a role only where its users span several divisions; a system role stays unscoped.** Chosen.
- **Load the legacy RBAC tables and transform them in SQL migrations.** Would make the migration chain depend on tables the schema has dropped; the transform stays in the pipeline, after the chain, like identity (#7).

**Decision:**

- **Where it runs and what it reads.** After the migration chain and the identity transform, as `transformRbac(client, snapshot)`. Unlike identity, which reads the replayed `master.users`, this transform reads the parsed snapshot: the role tables are never loaded, and migration `0030` has already dropped `users.division_id` by the time it runs.
- **The split rule.** For each legacy role, take the distinct divisions of the users who hold it. A **system role** (`is_system`) stays unscoped, keeping its name and UUID. A role whose users sit in **exactly one** division keeps its name and UUID and gets that division. A role whose users span **several** divisions becomes one copy per division, named `<Role> - <Division>`, each with a deterministic UUIDv5 derived from the legacy role id and the division id, so two rehearsals produce the same ids and comparable checksums. A small rename table, documented in `docs/migration/import-pipeline.md`, maps a seeded legacy name onto revamp's base name before the division is appended: today only `Manager Division` to `Manager`, so the copies read `Manager - Operations` and `Staff - Trucking` rather than `Manager Division - Operations`. Any other role name splits mechanically. The owner renames on the Roles screen afterwards if they wish.
- **Carried role fields.** `name`, `description`, `color_hex`, `icon_name`, `is_active`, `is_system`, `created_at`, `updated_at`. `level`, `guard_name` and `metadata` are dropped (D-012). A split copy inherits every field from its legacy role.
- **Constraints the new schema adds.** A colour that is not `#RRGGBB` falls back to the column default with a warning, as a stray icon does. Two legacy roles whose names differ only by case are a verifier error naming both; the second is not carried. An icon is rewritten by the same Heroicons-to-Lucide map migration `0032` used: that map moves into a TypeScript module next to the icon catalogue, a test asserts it equals the SQL, and a name with no counterpart emits the existing `icon-name` warning. The chain's rewrite never sees these rows because they are inserted after it.
- **Permissions.** Mapping is name for name: a legacy permission whose `name` is a catalogue key is carried, and `spatie.role_has_permissions` becomes `master.role_permissions`. No key is invented: a catalogue key with no legacy counterpart (roles `view_any` and `view`, say) goes only to Super Admin. A legacy permission with no catalogue key is a **warning**, aggregated per legacy resource with its action names, so the trucking, warehouse, expense and dashboard grants that have no keys yet do not drown the report. They stay in the snapshot and arrive by re-import once their modules catalogue their keys (ADR-0024's replay); there is no retention table.
- **Super Admin.** The system role named `Super Admin` is granted **every catalogue key**, and its legacy pivot rows are ignored: its legacy power came from a code bypass, not grants, and ADR-0045 requires the grants. No such role in the snapshot is a verifier error.
- **Assignments.** Each `spatie.model_has_roles` row plus that user's `users.division_id` picks the carried role or the copy for that division, and becomes a `master.user_roles` row. A user who holds a role but has **no division** is a verifier **error** naming user and role, with no assignment made and no second finding for being role-less. A Super Admin user's legacy division (Developer, Executive) is dropped without a finding: an unscoped role operates everywhere. A role scoped to a Trashed division is carried as it is.
- **Direct grants.** Rows in `spatie.model_has_permissions` have no counterpart: permissions reach a user only through roles. Each is a verifier **error** naming user and permission. The table is expected to be empty.
- **Role-less users.** A live user who ends with no role is a verifier **error**; Trashed and Suspended users are exempt. No default role is assigned.
- **The report** gains an `rbac` section with the counts of roles carried, roles split, grants, assignments and unmapped permissions, and the new finding codes join the table in `docs/migration/import-pipeline.md`.

**Trade-offs:** The rehearsal report will not be clean until the domain modules catalogue their keys, and `db:import` keeps exiting 1 on warnings, so the rehearsal (#18) reads the warnings rather than the exit code. The rename table bakes four production role names into the pipeline; it is documented and anything unknown degrades to the mechanical name. Splitting changes the id of a role used in several divisions, so nothing outside the snapshot may hold a legacy role id (nothing does: only the Spatie pivots reference roles). Errors on role-less users, division-less users and direct grants mean the operator fixes legacy data before cutover instead of the import guessing at access, which is the point: nothing in the pipeline silently repairs data, and nothing silently widens who may do what.
