# ADR-0019: Per-PR preview deployments

**Context:** ADR-0015 decided on a standing staging environment (separate `vmb-api-staging`/`vmb-web-staging` Workers/Pages targets plus a Neon staging branch) to give deploy and migration changes a dry run before production. The team prefers a preview per pull request instead of one shared environment, and Cloudflare provides the pieces natively: a Workers preview alias (`wrangler versions upload --preview-alias`), a Pages branch-alias deployment (`wrangler pages deploy --branch=…`), and Neon branching. Beyond ADR-0015, two things needed deciding: how each PR's web deployment learns _that PR's_ API URL, and where a preview's runtime secrets come from (ADR-0011 scopes fnox to local/CI dev secrets, not Worker runtime).

**Options considered:**

- Keep the standing staging environment (ADR-0015): one shared target to keep schema- and secret-synced with production. A change mid-test leaves it in a half-applied state, and two PRs cannot run migrations independently.
- Per-PR previews: an isolated Worker version, Pages deployment, and Neon branch per PR. No shared state to corrupt; migrations run against a throwaway database; the Worker side needs no cleanup (aliases LRU-prune, versions are CF-retained), while the Neon branch and Pages deployment do.
- API-URL wiring: (a) a Pages Preview environment variable — rejected, because Pages Preview variables are uniform across _all_ preview deployments, so every PR's web would point at one shared API URL; (b) inject the deterministic preview-alias URL (`pr-<n>-vmb-api.<account>.workers.dev`) at build time as `PUBLIC_API_URL`, which `resolveApiUrl()` prefers over the Pages binding.

**Decision:** Per-PR previews, replacing the shared staging environment as the dry-run mechanism. `preview.yml` creates a Neon branch named for the PR's alias, migrates it, uploads an `apps/api` version under the alias `pr<n>-<slug>` (the PR title sanitized the way Cloudflare does, prefixed with the immutable PR number — the branch name is the fallback; ADR-0029), builds and deploys `apps/web` on that same branch name with `PUBLIC_API_URL` set to the alias URL (Pages may truncate or disambiguate the alias it registers, so the posted web link is the URL `wrangler` reports — ADR-0029), and comments both URLs on the PR. After each successful web deploy `preview.yml` prunes the superseded Pages deployments — matched by the same `pr<n>-` prefix the cleanup uses — so an open PR keeps only the deployment it just made; `cleanup.yml` deletes the Neon branch and the PR's remaining Pages preview deployment(s) on close (merged or not), a safety net rather than the primary reaper (issue #84). The Neon branch now carries the alias too, so a retitle renames it in place rather than leaving a second branch behind (ADR-0029), and both reapers — the Pages sweep and the Neon delete — match every object whose name carries this PR number's `pr<n>-` prefix, or the `pr-<n>` fallback exactly, including ones orphaned by a rename that a current-name lookup would miss. The three preview resources are not alike (issue #55): a Workers preview alias needs no cleanup (LRU-pruned past 1000 concurrent aliases), a Workers version is CF-retained with no supported individual delete, but a Pages deployment is retained indefinitely and each push — and each branch rename — adds another, so it is pruned on each successful deploy and swept again at close. In practice every match is deleted, latest included, with `force=true` — measured 2 of 2 for a two-push PR (Cleanup run 35333457925) and 1 of 1 for a single-push PR, leaving 0 residuals (issue #68). Those runs cannot distinguish whether the documented latest-for-branch guard does not apply to preview aliases or `force=true` lifts it; either way no residual is left.

**One definition, one list, one opt-out.** The set of paths that count as a "code-relevant change" — what a build or deploy actually depends on — is defined once in `scripts/code-relevant-paths.sh`. Two gates consume it: `ci.yml`'s `Detect code-relevant changes` step, which decides whether a `master` push deploys (issue #63), and `preview.yml`'s `Detect Code-Relevant Changes` job, which decides whether a pull request gets a preview. The deploy gate takes the canonical list alone — a workflow edit cannot change the deployed artifact, so it must not force a deploy — while the preview gate adds `.github/workflows/**`, because a workflow edit still has to be exercised by the Preview run of the PR that makes it (ADR-0023). `.github/actions/**` is canonical on both, since the composite action chooses the toolchain and install flags a build uses; `.mise.toml` is canonical despite dev-only pins (e.g. `lefthook`) that never change a build, because the same file controls build-affecting pins (`node`, `pnpm`, `wrangler`) and a pathspec cannot separate the two (issue #70). `cleanup.yml` deliberately opts out entirely: it runs unfiltered, so a reverted final diff cannot strand a Neon branch or Pages deployment (issue #66). This replaces the hand-kept pair #70 recorded, in which `preview.yml`'s `on.paths` was canonical and `ci.yml` a copy. #83 reopened that call and evaluated three options. Keeping the pair in step by review was rejected because the dangerous drift is one-way and silent: a path added to Preview but not the deploy gate makes a `master` merge skip a needed release, the exact failure class ADR-0023 exists to prevent. A divergence guard was rejected for the second time, now as strictly worse than removing the pair: it would translate between YAML globs and shell pathspecs to police a divergence a shared definition cannot have. The single source costs Preview its trigger-level filter, because a workflow's `on.paths` cannot reference a shared value: `preview.yml` now runs on every pull request and a secret-free `changes` job decides whether the secret-bearing preview job starts. A docs-only PR therefore pays one cheap checkout-and-diff job rather than starting no run at all, and gains a named check that records why no preview was made; a workflow-only PR still self-tests the preview, and a code PR still runs it (issue #83). The module owns the classification and the fail-open policy — only a definitive "no code-relevant change" skips; a missing object or an unusable baseline runs the gate — so both gates read one decoder. The preview job takes `needs: changes` with `!cancelled()` rather than the default skip-on-failure, so a `changes` job that fails outright (runner, checkout) still runs the preview instead of silently skipping a code PR. The module also owns errexit-safety: `git diff --quiet` exits 1 as its normal "changes found" signal, which killed the deploy-gate step under the runner's inherited `bash -e` until #97 cleared it with `set +e`. That guard now lives inside `detect_code_relevant_change`, around the `git diff` it protects, so neither caller needs a bare `set +e` — the step cannot lose it by editing the code around it, and both gates inherit it (issue #83, superseding the caller-side fix #97 as the one place it is expressed).

The same "one definition" rule now covers the names. `scripts/preview-identifiers.sh` is the single definition of the alias — which is also the Neon branch name — and of the prefix and fallback both reapers match; `preview.yml` (create) and `cleanup.yml` (destroy) both source it, so a later change to the naming cannot make the two disagree and orphan a Pages deployment or Neon branch (issue #78). It is a behaviour-preserving extraction: the strings produced for a given PR number and branch name were unchanged by it — the slug's source moved from the branch to the title later, deliberately (ADR-0029). The module is shellchecked by the workflow-lint job, which already walks `scripts/**/*.sh` (issue #61).

The Pages deployment calls get the same treatment. `scripts/pages-preview-deployments.sh` holds the paginated lookup and the forced delete that both the per-push prune (`preview.yml`) and the close-time sweep (`cleanup.yml`) use, so the match predicate and the `per_page` cap cannot drift between them. The two still own their failure policy: the prune warns and moves on, the sweep fails the run (issue #84). It is shellchecked the same way, as part of `scripts/**/*.sh`.

Preview runtime secrets: shared values (`BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`) come from the fnox store CI already decrypts, the three per-PR values (`DATABASE_URL`, `BETTER_AUTH_URL`, `WEB_URL`) are supplied per upload via `wrangler versions upload --secrets-file`, and that same secrets file pins `EMAIL_TRANSPORT: "log"` so the preview logs outbound mail instead of handing it to Resend (issue #121). This is a deliberate, narrow exception to ADR-0011: fnox feeds only ephemeral preview versions, never the production deployment, whose secrets stay in `wrangler secret` / the dashboard. A preview version's secrets attach to that version alone and do not alter the deployed production version.

**Standing staging environment — Pages half removed as a platform requirement, API half left pending a decision.** Cloudflare Pages supports only the named environments `preview` and `production`; wrangler rejects any other environment name, so ADR-0015's `[env.staging]` block in `apps/web/wrangler.toml` failed _every_ `wrangler pages deploy` and has been removed. The `apps/api` `[env.staging]` block (`vmb-api-staging`) is still valid on Workers and is left untouched, per issue #23's instruction not to remove staging silently. With no web counterpart it can't function as a staging _environment_, though; per-PR previews now cover the dry-run need that motivated ADR-0015. What remains to decide is whether the API staging block earns its keep for anything previews don't cover (a stable demo URL, manual QA outside a PR). Until then it stays as-is, unprovisioned.

**Preview data policy: parent pinned to production, data synthetic-only (issues #118, #120).** The Neon branch parent is pinned explicitly to `production` and the database to `app` (renamed from `vmb`, ADR-0029) — the database production actually uses — rather than left to the project defaults, where `database` silently resolved to `neondb` and `parent_branch` to whichever branch was default at the time (issue #118). Production is the parent for one property: the branch inherits the schema and the `drizzle.__drizzle_migrations` journal, so a preview applies just the PR's new migrations instead of replaying the chain from `0000`. The existing dev Neon branch (ADR-0024) was rejected as parent because nothing keeps it at production's head, and a drifted parent would silently reintroduce exactly that replay. Because a production-parented branch also inherits production's rows, and a preview URL is unlisted but public, `preview.yml` wipes every row in `public`, `master`, `trucking`, `warehouse` and `expense` and inserts deterministic fixtures — in one transaction, after migration and before the API version is uploaded, so a failed seed rolls back and fails the run rather than half-emptying a live preview (issue #120). The wipe runs on every preview run, not only at branch creation, so each push starts from the same dataset; `drizzle.__drizzle_migrations` survives because it lives in its own schema. Previews therefore never serve a production record, and the data policy is a property of the pipeline rather than of who holds the URL: unlisted URLs need no Cloudflare Access gate while that holds. Previews sign in through a seeded, verified credential user, so clicking through the UI never depends on sign-up, and previews send no real transactional email (issue #121). Branch `expires_at` (30 days) is a safety net for a run that dies before `cleanup.yml` sees the PR close (issue #118).

**Fork PRs are not previewed (ADR-0030).** The per-PR promise above holds for same-repo PRs only (issue #149): GitHub passes no repository secrets to a `pull_request` run from a fork, so `preview.yml`'s `preview` job and `cleanup.yml`'s `cleanup` job both require `github.event.pull_request.head.repo.full_name == github.repository` and conclude `skipped` for a fork PR instead of failing at its first secret-dependent step. Plain `pull_request` stays the trigger; `pull_request_target` was rejected for handing production-capable credentials to unreviewed code (ADR-0030).

**Schema diff on the preview comment (issue #153).** The sticky comment also reports how the preview branch's schema differs from production's, so a reviewer sees the change itself and not only that migrations ran. `preview.yml` compares the preview branch — the target, after migration — against `production` (`NEON_PARENT_BRANCH`, the branch previews fork from, resolved to its branch id in the same step) through Neon's `compare_schema` endpoint, and renders a bounded excerpt inside a `<details>` block: an empty diff becomes an explicit "no schema changes", and a comparison that cannot be made becomes "unavailable — see the workflow run" rather than a red run. Neon's `schema-diff-action` was rejected as the mechanism: it runs on Node 20 and last released v1.0.1 (2025-01-03), while the endpoint is a `curl` plus markdown in code the repo already owns. The comparison is deliberately non-blocking — a UX add-on must not fail a preview that otherwise deployed — and the excerpt is bounded twice (200 lines in the step, then 20,000 characters in the comment step) with the full diff left in the workflow-run log, so the body stays comfortably inside the comment API's 65,536-character limit.

**Trade-offs:** Every PR push spends CI minutes, a Neon branch, and a Pages deployment. Neon caps branches and Cloudflare retains Pages deployments indefinitely, so reaping is load-bearing for both resources: the Neon branch at close, and the Pages deployments per successful push with close as the safety net (issue #84) — hence the shared concurrency group that cancels an in-flight preview before deleting. No Pages residual is left: an open PR keeps one deployment (the latest), and a closed PR keeps none, because the sweep deletes the last one too, latest included (issue #68). In return there is no shared environment to keep in sync, migrations get a genuinely isolated database, and an in-flight PR cannot touch production. One measured limitation drives a later decision: Cloudflare does not emit logs for preview URLs — `wrangler tail`, Workers Logs, and Logpush are all unavailable there — so runtime measurements that need logs (e.g. ADR-0012's scrypt CPU-time check, tracked in issue #21) must run against a real deployment (production, or a named staging Worker), not a preview.
