# ADR-0019: Per-PR preview deployments

**Context:** ADR-0015 decided on a standing staging environment (separate `vmb-api-staging`/`vmb-web-staging` Workers/Pages targets plus a Neon staging branch) to give deploy and migration changes a dry run before production. The team prefers a preview per pull request instead of one shared environment, and Cloudflare provides the pieces natively: a Workers preview alias (`wrangler versions upload --preview-alias`), a Pages branch-alias deployment (`wrangler pages deploy --branch=…`), and Neon branching. Beyond ADR-0015, two things needed deciding: how each PR's web deployment learns *that PR's* API URL, and where a preview's runtime secrets come from (ADR-0011 scopes fnox to local/CI dev secrets, not Worker runtime).

**Options considered:**
- Keep the standing staging environment (ADR-0015): one shared target to keep schema- and secret-synced with production. A change mid-test leaves it in a half-applied state, and two PRs cannot run migrations independently.
- Per-PR previews: an isolated Worker version, Pages deployment, and Neon branch per PR. No shared state to corrupt; migrations run against a throwaway database; everything self-cleans except the Neon branch.
- API-URL wiring: (a) a Pages Preview environment variable — rejected, because Pages Preview variables are uniform across *all* preview deployments, so every PR's web would point at one shared API URL; (b) inject the deterministic preview-alias URL (`pr-<n>-vmb-api.<account>.workers.dev`) at build time as `PUBLIC_API_URL`, which `resolveApiUrl()` prefers over the Pages binding.

**Decision:** Per-PR previews, replacing the shared staging environment as the dry-run mechanism. `preview.yml` creates a Neon branch named `pr-<n>`, migrates it, uploads an `apps/api` version under the alias `pr-<n>`, builds and deploys `apps/web` on branch `pr-<n>` with `PUBLIC_API_URL` set to that alias URL, and comments both URLs on the PR; `preview-cleanup.yml` deletes the Neon branch on close (merged or not). No cleanup is added for the Workers alias or the Pages deployment — Cloudflare's docs confirm neither needs it.

Preview runtime secrets: shared values (`BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`) come from the fnox store CI already decrypts, and the three per-PR values (`DATABASE_URL`, `BETTER_AUTH_URL`, `WEB_URL`) are supplied per upload via `wrangler versions upload --secrets-file`. This is a deliberate, narrow exception to ADR-0011: fnox feeds only ephemeral preview versions, never the production deployment, whose secrets stay in `wrangler secret` / the dashboard. A preview version's secrets attach to that version alone and do not alter the deployed production version.

**Standing staging environment — Pages half removed as a platform requirement, API half left pending a decision.** Cloudflare Pages supports only the named environments `preview` and `production`; wrangler rejects any other environment name, so ADR-0015's `[env.staging]` block in `apps/web/wrangler.toml` failed *every* `wrangler pages deploy` and has been removed. The `apps/api` `[env.staging]` block (`vmb-api-staging`) is still valid on Workers and is left untouched, per issue #23's instruction not to remove staging silently. With no web counterpart it can't function as a staging *environment*, though; per-PR previews now cover the dry-run need that motivated ADR-0015. What remains to decide is whether the API staging block earns its keep for anything previews don't cover (a stable demo URL, manual QA outside a PR). Until then it stays as-is, unprovisioned.

**Trade-offs:** Every PR push spends CI minutes and a Neon branch, and Neon caps branches, so the close-time cleanup is load-bearing rather than optional (hence the shared concurrency group that cancels an in-flight preview before deleting). In return there is no shared environment to keep in sync, migrations get a genuinely isolated database, and an in-flight PR cannot touch production. One measured limitation drives a later decision: Cloudflare does not emit logs for preview URLs — `wrangler tail`, Workers Logs, and Logpush are all unavailable there — so runtime measurements that need logs (e.g. ADR-0012's scrypt CPU-time check, tracked in issue #21) must run against a real deployment (production, or a named staging Worker), not a preview.
