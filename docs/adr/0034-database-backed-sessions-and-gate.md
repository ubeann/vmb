# ADR-0034: Database-backed sessions, gated at creation and bridged to apps/web

**Context:** #7 had to document the session/token strategy, extending ADR-0012 (Better Auth) and ADR-0018 (required verification without auto-sign-in). The pieces around it were decided separately: the durable business record and identity ownership (ADR-0032), activation for migrated accounts (ADR-0033), and the removal of public sign-up. What remained was the session itself: where it lives, how long it lasts, how a browser on apps/web receives a cookie set by apps/api, and where the "may this person be signed in at all" check sits.

**Options considered:**

- **Stateless tokens (JWT) or Better Auth's `session.cookieCache`.** Fewer database reads, but revocation becomes eventual: a soft-deleted user's existing cookie keeps working until expiry. Rejected — offboarding is the one case the gate exists for.
- **A shared cookie domain (`advanced.crossSubDomainCookies`).** Impossible here: apps/web (Pages) and apps/api (Workers) are different registrable domains, not subdomains of one.
- **Link-based activation and magic-link sign-in.** Rejected in ADR-0033: the emailed link lands on the API origin, where the session cookie never reaches apps/web — the reason ADR-0018 forbids auto-sign-in after verification. OTP codes typed into the web UI cross the existing bridge instead.
- **Database-backed sessions with the `sveltekitCookies` bridge, gated at creation.** Chosen.

**Decision:**

- A session is a row in `public.session`, created by Better Auth. Lifetimes are Better Auth's defaults, deliberately not overridden: a 7-day absolute expiry, refreshed after 24 hours of use; no cookie cache, so the database is the source of truth and revocation takes effect on the next request. Soft-deleting a user revokes all of their sessions in the same store operation.
- The cookie is httpOnly, `SameSite=Lax`, `Secure`, set on the API's response and forwarded onto apps/web's own response by `sveltekitCookies` (server-side form actions and hooks call the API directly, so the browser never needs to see the API's `Set-Cookie`).
- Every session is created through one gate: `databaseHooks.session.create.before` (`apps/api/src/sign-in-gate.ts`) rejects a user whose `master.users` row is missing or soft-deleted with `403 ACCOUNT_UNAVAILABLE`, covering every session-creating path — password sign-in, OTP activation, and anything added later. Resource-level authorization is #8's, deliberately not here.
- Web routes gate in one place: the root layout server guard with a public allowlist (`/login`, `/activate`, `/logout`); a new page is protected unless someone deliberately names it public. API routes gate with `requireSession` on `/api/master/*`; `/health` and `/api/auth/*` stay open by construction.
- Credentials are Better Auth's default scrypt in `public.account`. Migrated accounts carry none and activate by email OTP (ADR-0033); admin-created users (Master CRUD) get one and verify their email via ADR-0018's link before password sign-in is allowed.
- Sign-up is disabled on both `emailAndPassword` and the OTP plugin; users are provisioned by admins, as in the legacy app.
- Logout is best-effort: the API destroys the session and clears the cookie, and apps/web redirects to `/login` even if the API is unreachable rather than trapping the user on a failed action.

**Trade-offs:** Every authenticated request pays a session lookup (and session refresh at most once a day), where a signed token would pay none — accepted for immediate revocation, and the lookup is one indexed row beside the query the request was going to make. The gate reads the business record on session creation only, not per request, so a record soft-deleted mid-session stays usable until the store's revocation lands or the session expires; that window is one request with no cache in front of it. The public allowlist means a new public route is a deliberate edit to one set rather than a layout placement, which is the point: forgetting is safe in the other direction.

**Amendment (2026-09-29, #206):** `/login` has a "Remember me" checkbox, **unticked by default** as in the legacy Filament login, so there are two lifetimes. Both are Better Auth 1.7's own `rememberMe` behaviour, still not overridden:

- **Ticked** (`rememberMe: true`): the session above — a persistent cookie (`Max-Age` 7 days) and a row that expires after 7 days, refreshed after 24 hours of use.
- **Unticked** (`rememberMe: false`): a browser-session cookie (no `Max-Age` or `Expires`), so it ends when the browser closes. Better Auth also caps the row at 24 hours from sign-in and never refreshes it, so the session ends at whichever comes first. It sets a signed `dont_remember` cookie, also browser-session, beside the session token.

The `dont_remember` cookie is what keeps an unticked session non-persistent. On each session read, a refresh-due session is re-issued with a 7-day `Max-Age` unless the request carries `dont_remember`, and an unticked session is refresh-due from the start (its 24-hour expiry sits more than a day short of the 7-day window). So the bridge must carry both cookies both ways: `apps/web/src/lib/auth.ts` re-sets every `Set-Cookie` Better Auth emits without adding an expiry of its own, and `hooks.server.ts` forwards the browser's whole `Cookie` header to the session read. `apps/web/src/lib/auth.test.ts` proves this against a real Better Auth instance, including the control case where dropping `dont_remember` re-persists the session. Any other caller that reads the session with the browser's token — `requireSession` on `/api/master/*` included — must likewise receive the whole `Cookie` header, never the session token alone, or that read refreshes an unticked session's row out to 7 days. Sign-out expires both cookies.

**Trade-offs of the amendment:** unticked is stricter than before (a shift longer than 24 hours signs the user out mid-browser-session), accepted because shared warehouse machines are the case the checkbox exists for. Browsers that restore the previous session on relaunch also restore session cookies; that is the browser's choice and outside VMB's control, and the 24-hour row cap still bounds it. Ticked is shorter than the legacy app's Laravel recaller cookie, whose `remember_token` column is dropped (D-004); the 7-day sliding session replaces it.

**Amendment (2026-09-29, #226):** The bridge's other direction is explicit too. SvelteKit's `event.fetch` forwards the browser's cookies only to apps/web's own host and its subdomains, so across registrable domains apps/api received none: logout cleared the browser's cookies but left the `public.session` row valid, and `requireSession` saw no session on `/api/master/*`. The access seam (`apps/web/src/lib/api-access.ts`) now adds the browser's whole `Cookie` header to every API call, which covers `hooks.server.ts`'s session read as well. A cookie-carrying POST must pass Better Auth's origin check. `event.fetch` sends apps/web's own origin as `Origin`, so that origin must stay in apps/api's `trustedOrigins` (`WEB_URL`). Logout stays best-effort, and a sign-out the API refuses is logged rather than dropped. `apps/web/src/lib/auth.test.ts` proves against a real Better Auth that the old cookie no longer authenticates after logout.

**Trade-offs of the amendment:** Auth calls that sent no cookie before, such as activation's password-reset endpoints, now carry any cookie the browser still holds, so they too pass through the origin check. A host that reaches apps/web under any origin other than `WEB_URL` (a Cloudflare alias suffix on a preview, a `*.pages.dev` production URL) is refused, where sign-in already was.

**Amendment (2026-10-06, D2):** The gate and the revocation also decide on a user's `status`, which the decision above did not record. A session is created only for an **Active** user: `apps/api/src/sign-in-gate.ts` refuses a user whose `master.users` row is missing or soft-deleted, and also one whose status is Suspended or Inactive, all with the same `403 ACCOUNT_UNAVAILABLE`. The GLOSSARY's _Suspended User_ entry defines the two: a Suspended User is expected back, and an Inactive User has left. Trashed is the third way out, a soft-delete. While a user is Suspended or Inactive, saving them revokes all of their sessions (`packages/db/src/master/users.ts`, `updateUser`), after the save commits, so a cookie already issued stops working on its next request. A session that survives grants nothing: each request's permission read (`packages/db/src/master/access.ts`) holds only for an Active, not-Trashed user (ADR-0045).

**Trade-offs of the amendment:** The gate reads `status` only when a session is created, and the revocation runs after the save commits rather than inside its transaction, so a session can outlive a status change by one request; the per-request permission read closes that window for anything it guards. Keeping Suspended and Inactive as separate statuses, both refused, leaves three states that all mean "cannot sign in"; the glossary keeps them apart by meaning, not by behaviour.
