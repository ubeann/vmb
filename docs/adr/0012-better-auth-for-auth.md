# ADR-0012: Auth provider — Better Auth (self-hosted)

**Context:** `ARCHITECTURE.md` §8 originally decided Clerk (managed, free tier) — see the superseded rationale below. Revisited after checking Better Auth's docs against this project's actual stack: it officially supports mounting directly on Hono (Web Standard `Request`/`Response`, no adapter needed), runs on Cloudflare Workers with the `nodejs_compat` flag (already set in both `wrangler.toml` files for `AsyncLocalStorage`), has a documented SvelteKit integration (`hooks.server.ts` + `svelteKitHandler` + client), and its Drizzle adapter reuses `packages/db` directly — no second data store or vendor schema.

**Options considered:**

- Clerk (managed, free tier): hosted UI/session/MFA, but sits beside the stack as a separate vendor rather than integrating with it, and adds a free-tier MAU ceiling.
- Better Auth (self-hosted library, not roll-your-own): 2FA/passkeys/OAuth/SSO built in, so the "self-hosted = build auth from scratch" cost that originally favored Clerk mostly doesn't apply — it's a library, not a from-scratch build.
- Neon Auth / Managed Better Auth (**re-evaluated 2026-09-18, issue #21**): now GA and genuinely built on Better Auth — auth data in the `neon_auth` schema, branchable with the database — which would remove the scrypt CPU cost from `apps/api` entirely. Rejected again, on concrete blockers for *this* stack: (1) Neon Auth's roadmap states standalone frontend + backend on **different domains is not yet supported**, because its HTTP-only session cookie cannot be securely shared across domains — which is exactly the `apps/web` (Pages) + `apps/api` (Workers) split that our `sveltekitCookies` bridge exists to handle; (2) no SvelteKit or Hono SDK (Next.js server SDK plus React/Vite/TanStack clients only); (3) it pins Better Auth **1.4.18** while we run **1.7.4**, so migrating is a downgrade gated by Neon's upgrade cadence; (4) `@neondatabase/auth` deliberately restricts the option/plugin surface (Organization partial, MFA "coming soon", no custom plugins/hooks), while we rely on `sveltekitCookies` and a custom `sendVerificationEmail`; (5) auth leaves our Drizzle schema for `neon_auth`, ending type-safe joins with domain tables and requiring per-branch (including per-PR) provisioning plus trusted-domain registration. Revisit if standalone-architecture support and a SvelteKit server path ship; the CPU motivation is weak while the deployment runs uncapped (see the measurement outcome below).

**Decision:** Better Auth, self-hosted, mounted directly inside the existing `apps/api` Hono Worker and wired to `packages/db`.

**Known risk, accepted with a measurement plan:** Better Auth's default password hashing (scrypt) is deliberately CPU-intensive, and Cloudflare Workers' **free-tier** CPU limit is 10ms/request (Paid: 30s default, up to 5 min) — a login/signup request could exceed the free-tier budget. Given this app's small internal user base, registrations/logins are infrequent, not steady load, so the practical risk is low. Plan: ship it, measure actual scrypt CPU time against the free-tier limit in production (Workers request logs), and only then decide whether to (a) do nothing, if it fits, (b) upgrade `apps/api` to Workers Paid ($5/mo) if it doesn't, or (c) restrict to OAuth-only sign-in (Google/GitHub), which sidesteps password hashing entirely and stays free. Don't pre-optimize for (b)/(c) before the measurement says it's needed.

**Measurement outcome (2026-09-18, issue #21):** scrypt costs **~130–175ms of CPU per signup/login** in production (`wrangler tail`: signup 137ms; logins 131/149/175ms unverified and 152ms verified; a no-hashing baseline, `GET /api/auth/ok`, is 2–40ms, so essentially all of it is password hashing). The account, however, is on the Workers **Free** billing plan (dashboard: "Workers Free", no payment method), whose documented limit is **10ms CPU per invocation** — by the docs, this workload should fail. It does not in practice: the Worker's `usage_model` is `standard` (the account's `default_usage_model` is also `standard`), and a scratch Worker deployed into the same account burned **1,563ms of CPU with `outcome: ok`** — no `exceededCpu`. The 10ms Free cap is therefore not being enforced here, and scrypt runs far below whatever limit is in effect. That is an unusual state for a Free account, though: the docs tie the 10ms cap to Free and the `standard` model to Paid, and there are reports of `standard` silently reverting to the older `bundled` (50ms) cap — still below scrypt's ~137ms, which would break auth with `exceededCpu`. **Recommendation: option (b)** — upgrade `apps/api` to Workers Paid ($5/mo) — makes the 30s Standard limit contractual and removes the ambiguity; option (c) OAuth-only remains the free fallback if the CPU budget is unwanted. Until (b) lands, the deployment works on the empirically-observed uncapped model, with the revert risk above unmitigated.

**Trade-offs:** Owning the login/signup UI (Clerk gives one for free) and carrying the CPU-limit risk above, in exchange for no external auth vendor, no MAU ceiling, and direct reuse of the Drizzle/Neon setup already built for this project (more consistent with ADR-0009's minimal-moving-parts/$0-cost bias than Clerk was).
