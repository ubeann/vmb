# ADR-0045: Permissions are enforced at the API, from role grants

**Context:** #8 needs a rule for who may do what. Until now `requireSession` only proved someone was signed in, so any signed-in user could create users or delete roles. Legacy decided access in Spatie with a `Gate::before` bypass for Super Admin, divisions compared by name in 58 places, and a catalogue synced from code that hard-deleted whatever code no longer listed. `docs/research/master-entities-review.md` records the findings and the legacy `revamp` branch's design this follows.

**Options considered:**

- **Check permissions in each SvelteKit load and action.** Hides screens, but the API stays open to anyone who can send it a request.
- **A Super Admin bypass in code.** One more mechanism to audit, and the role matrix stops being the whole truth.
- **Roles carry permission grants, and the API checks them on every route.** Chosen.

**Decision:**

- A **Role** grants **Permissions** (`master.role_permissions`); a **User** holds Roles (`master.user_roles`). A user's permissions are the union of their **active** roles' grants. Nothing subtracts, and an inactive role grants nothing.
- The catalogue of permissions is defined in code (`packages/types/src/permissions.ts`) and projected into `master.permissions`. The catalogue is loaded by migration (`0031` carries today's keys) and a test fails when the migrations and the code disagree; a key joins or leaves the catalogue by a migration, never by a sync that deletes. Grants are written by the legacy RBAC import (#311) and, later, a permission matrix on the Roles screen; until then a Role created through the API holds nothing.
- Every `/api/master/*` route names the one permission it needs (`requirePermission("master-users.create")`) and answers 403 without it. A test checks its table of routes and keys against the routes the app registers, so an unguarded route or a wrong key fails.
- Super Admin is a System Role holding every key through ordinary grants. There is no environment-variable user id, no role-name check and no bypass; a test fails if a catalogue key has no Super Admin grant.
- **Division scopes a role, and never grants.** `roles.division_id` says where a role operates (null: everywhere). Code never compares division names. Nothing filters Master records by it yet: the scope applies to the records the domain modules add (items, budgets, requests), which is where an `all_division` key will come in.
- **Changing a user needs at least their permissions.** A caller may only add or remove a role whose permissions they hold, and may only edit, suspend, delete or restore a user whose roles' permissions they hold (people may always edit themselves). Without the second rule `master-users.update` alone would reset a Super Admin's password. Omitting `roleIds` on an update leaves the roles alone.
- A suspended or Trashed user holds no permissions even if a session survives.
- The caller's own access is `GET /api/me`, open to every signed-in user: the shell reads permissions and division from it instead of from the Users and Divisions resources, which only someone permitted to read them may call.

**Trade-offs:** The role check and the write are separate statements (the Neon HTTP driver has no interactive transactions), so a concurrent role change can slip between them; the write removes only the roles the check covered. Nothing stops the last Super Admin removing their own role, and a Finance-scoped manager may grant any role whose permissions they hold, whatever its division. One extra indexed query per protected request (permissions are not cached, so a revoked grant takes effect on the next request, matching ADR-0034's reasoning for sessions). Until roles are assigned to users, nobody holds a permission, so a database without role data refuses every Master route; the legacy RBAC export must run before cutover, and previews are seeded so they work. The web hides what the API would refuse as a courtesy only; the API is the enforcement.

**Amendment (2026-10-07): what a permission check costs.** The "one extra indexed query" above did not hold. `requirePermission` called `getAccess`, which runs three queries one after another (the user's status, their permissions, and their divisions, which a permission check never reads), and `assertCanManageUser` and `assertCanChangeRoles` each called it again for the same caller, so a `PATCH /api/master/users/:id` that changes roles ran the caller's access three times before its write. Now:

- `requirePermission` reads the caller's permissions in one query: the grants of their active roles, and none unless the user is Active and not Trashed.
- That result is kept for the rest of the request, and the role and user guards take it rather than reading the caller's access again.
- Nothing is cached across requests, so a revoked grant still takes effect on the next request. If the check ever shows up in latency, the next step is a cache guarded by a version stamp that changes whenever a role's grants or a user's roles change, so each request reads only the stamp. A Bloom filter is not that step: its "maybe" must still go to the database, since treating it as "yes" grants on a false positive, and most requests are allowed ones.
- A test counts the statements a request runs against PGlite and fixes the budget, so a later change cannot quietly add round trips.
- `GET /api/me` still returns divisions, with its queries run in parallel.

The race in the trade-offs above, where a concurrent role change slipped between the role check and its write, closed when that check and write moved into one transaction that first locks the target user's row (ADR-0049, #335).

**Amendment (2026-10-12): the other writes close the same race in the statement (#413).** The transaction above covers a save that changes roles. A delete, and a save that keeps the roles, still checked the caller's reach (`assertCanManageUser`) as its own statements and wrote in another, so a role granted to the target in between let the write land on a user the caller could no longer manage. Both reviewers of PR #358 flagged it. These writes close it in `master`'s own style rather than with a transaction: the reach test goes into the write's `where` (`withinReach`, `not exists` over the permissions the target's active roles grant that the caller lacks), as `deleted_at is null` and `DIVISION_IN_USE` do (ADR-0055). The check ahead of the write stays and answers first with its own message; the test in the statement is the backstop. A write that matches no row reads once to say why, in this order: 404 (gone or Trashed), 403 `PERMISSION_ESCALATION` (the caller's reach), 409 `STALE_RECORD`. A caller's own user is exempt, as in the guard. What remains is the window inside that single statement, accepted as it is for the division delete. The happy paths cost the same statements as before (a delete 4, a save that keeps the roles 6); only a refused write adds the read that words its refusal.
