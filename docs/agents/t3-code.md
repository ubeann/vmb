# T3 Code: the tools the loop relies on

Checked 2026-10-12 against T3 Code server `0.0.46-nightly.20261011.2980`. T3 ships nightly, so its MCP tool list moves; the last section says how to re-check it. Tool names carry the harness prefix (`mcp__t3-code__…`); this doc uses the bare names.

## In use

| Tool                                                   | Where                                                                                                                                      |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `t3_thread_launch` with `workspaceStrategy`            | The dispatcher launches one build per ticket in a fresh worktree (`ticket-loop.md`). Only from full-access.                                |
| `orchestrator_capabilities`                            | Resolves provider instance and model IDs for a tier (`model-routing.md`).                                                                  |
| `link_pull_request`, `watch_pull_request`, `unwatch_…` | A build links its PR and lets T3 wake it on checks and comments; it unwatches when it hands back.                                          |
| `schedule_task`, `fixed_time`                          | The dispatcher windows and the morning digest.                                                                                             |
| `update_scheduled_task` with `bindToCurrentThread`     | Binds a task to the thread the call is made from, so its runs post there on that thread's model (`ticket-loop.md`, The dispatcher thread). |
| `t3_thread_send`                                       | The owner's steer into a running build: a review round posted from the dispatcher thread.                                                  |
| `delegate_task`, `task_status`, `task_cancel`          | The cross-provider review on a `complex` ticket; `role: review`, a target from `orchestrator_capabilities`.                                |
| `write_pull_request_guides`                            | The digest writes a review tour for every `needs-decision` PR, so the owner reads a guide instead of a diff. On since 2026-10-12.          |
| `preview_open`, `preview_navigate`, `preview_snapshot` | A quick look at a page; the screenshot scripts in `page-checks.md` cover every viewport.                                                   |

## Gotchas

- `t3_thread_launch` is refused from any mode but full-access; the dispatcher thread runs in that mode for this reason.
- `t3_thread_read` of a long thread exceeds the tool-result limit (137 K characters on a 1,898-item thread); page with `limit` and `afterPosition`, or extract from local storage with the `t3-thread-handoff` skill, which costs far less than reading the thread.
- A background command is stopped after two hours at most. A dev server that must outlive that is started detached (`page-checks.md`, Local dev servers).
- The harness blocks `sleep`; a build waits through `watch_pull_request` and a Monitor. A command that runs past the Bash tool's 120-second default is moved to the background and killed after 30 minutes; one slow `gh` call in a loop cost a dispatcher run 42 minutes on 2026-10-11. The dispatcher and the digest read GitHub through one script each (`scripts/frontier.sh`, `scripts/digest.sh`), a single GraphQL call that finishes in seconds.
- Every thread, the dispatcher, the digest and PR watching share one GitHub rate limit of 5,000 requests an hour. Until 2026-10-12 that was the owner's token, and it ran out twice in two days; Claude Code shells now run as the `vmb-agent` account (`harnesses.md`), so agent traffic and the owner's are counted apart. Threads on the other harnesses still share the owner's limit.
- A scheduled task runs on the model of the thread it is bound to, never on a tier; an unbound task takes the project's default model. Changing a task's tier means re-binding it from a thread on that model (`ticket-loop.md`, The dispatcher thread). An unbound task created from a thread in a worktree failed on 2026-10-11 with a worktree-provisioning error while the same tasks created from the web UI ran; unverified, so create or bind tasks from a thread on the project root.
- `delegate_task` needs a provider whose `canRunChildTask` is true in `orchestrator_capabilities`; Codex reported a status timeout on 2026-10-11, so the review fallback order in `model-routing.md` applies.

## Keeping this current

Once a month, or after a T3 update that changes the tool list: call `orchestrator_capabilities`, list the `mcp__t3-code__*` tool names the harness exposes, and compare both with this doc. A new tool goes under _To adopt_ with the place it fits, or is noted as not needed; a removed one leaves the tables. Record the server version and date at the top. A scheduled task can do the comparison and put the differences in the morning digest.
