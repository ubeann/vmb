# Master parity audit: legacy Master module against `master`

Audit date: **2026-10-17**. Question: can #6 ("Master: Divisions, Roles, Users") close, and which legacy Master logic has not moved over yet. The owner wants every piece of legacy logic across before anything new is built on top of it (#306 was closed for that reason).

Legacy is `ubeann/vmb-warehouse@development` at `ce03b9e` (2026-10-08), the deployed baseline (`docs/agents/legacy-reference.md`); `revamp` at `5fe7582` is cited where the owner's own redesign already settled a shape. This repo is `master` at `9e9cb91`. Citations: `vmb-warehouse@development:path:line` for legacy, `path:line` for this repo. This document supersedes `master-entities-review.md` (2026-10-06) for **status**; that review keeps the findings and the decisions D1–D7 the owner accepted.

The eight owner decisions were taken on 2026-10-17 ([section 10](#10-owner-decisions)); the rows below show the verdict after them. F8 in the profile section is not counted (nothing to carry).

What the numbers say:

- **The three entity screens are at parity or past it**, with four small misses (a Role filter on Users, a Role's Division on its form, bulk activate for Divisions, "at least one role").
- **The one large Master gap is the Roles form's permission matrix** (legacy `RoleFormBuilder`). Without it a Role created in VMB grants nothing, and the only way grants exist is the import. #8's checklist names it; no ticket does.
- **The profile page did not move at all**: personal information, password change, login sessions, two-factor and delete account. #115 covers only timezone and language.
- Everything the old review listed as "RBAC not started" is built: permission catalogue, API enforcement, role assignment with the escalation guard, the status gate, and the legacy RBAC import (ADR-0045, ADR-0056, PRs #308–#312, #455).

Verdicts: **done** (cites the code), **covered** (an open ticket owns it), **gap** (needs a ticket, proposed in [section 11](#11-proposed-gap-tickets)), **deviation** (a recorded decision replaced the legacy rule), **decision** rows were resolved on 2026-10-17 and now read as one of the other four, with the question cited.

## 2. How the audit was done

Four read-only inventories: legacy models, enums, scopes, traits, policies and the permission framework; the three Filament resources with their helpers; the profile page, two-factor service, seeders, schema and the `revamp` diff; and this repo's schema, store, types, API, pages, seed and import. The verdicts below are mine, checked against the code where a row decides something. Business modules (Trucking, Warehouse, Expense) and the System Log page were not audited; Master rules that exist to serve them are listed as dependencies in [section 13](#13-dependencies-for-the-business-modules).

## 10. Owner decisions

Asked one at a time on 2026-10-17. Q1 is recorded as an ADR-0045 amendment; Q2 and Q3 as ledger rows D-015 and D-016; Q6 gets its object-storage ADR with T7e; the rest are ticket scope.

### Q1. Who may edit a Role's grants?

Legacy hid the super-admin-only permission groups (every Master group, Trucking, the System Log) from a non-super-admin's matrix and stripped them from the request on save, so a non-super-admin could edit a role's Warehouse grants but never its Master grants (R8). The new model has no super-admin flag, so that rule cannot be copied as written.

**Recommendation:** the same rule as role assignment (ADR-0045): a caller may **add or remove only a grant they hold themselves**, and may edit only a role whose every grant they hold; System Roles stay uneditable for everyone. One rule for both screens, no per-resource flag, and the test suite's escalation cases extend to grants. Record as an ADR-0045 amendment.

**Answer (2026-10-17):** only grants you hold, as recommended. ADR-0045 amendment of the same date.

### Q2. Two-factor: a login factor, legacy's step-up only, or drop it?

Legacy 2FA never challenged at login (F4); it only guarded a few profile actions, its recovery codes were never consumed, and D-002 already drops the secrets. Options: (a) Better Auth's `twoFactor` plugin as a real second factor at sign-in, TOTP plus backup codes, opt-in per user, with a password step-up to enable or disable; (b) copy legacy: enrol, show codes, ask the PIN only before sensitive profile actions; (c) drop 2FA.

**Recommendation:** (a). A second factor that is never asked at sign-in is parity with a defect. Opt-in, not mandatory for any role yet (legacy mandated nothing); mandating it for Super Admin can be a later one-line policy. Record as an ADR (login flow, recovery, what happens to a user who loses the device: an admin disables it from the Users form).

**Answer (2026-10-17):** **drop two-factor.** Not carried; ledger row D-015. T7d is withdrawn. Revisit only when the business asks, with Better Auth's plugin as the path.

### Q3. Self-service account deletion: carry or drop?

Legacy let any signed-in user soft-delete their own account after a password prompt (F6). Accounts are provisioned by admins (no sign-up, ADR-0034), the legacy flow left other sessions alive and its page copy promised things the code never did, and a Super Admin deleting themselves can lock the system.

**Recommendation:** **drop it** as a deliberate deviation (a ledger row, no ADR): offboarding is an admin's act in Master, and the admin path already revokes every session. If the owner wants it kept, it becomes T9: password confirm, refuse when the user is the last active holder of a role that grants every key, revoke all sessions.

**Answer (2026-10-17):** drop it, as recommended. Ledger row D-016; T9 is withdrawn.

### Q4. Hide out-of-reach records, or show them read-only?

Legacy hid Super Admin users and System Roles from non-super-admins (R14, U14). The new app shows them to anyone with `view_any` and refuses the write at the API with 403 `PERMISSION_ESCALATION`; the page still offers Edit and Delete first.

**Recommendation:** **show them read-only.** Hiding was a courtesy with a leaky `orWhere`, and the reach check is the real protection. Carry the courtesy properly: an out-of-reach user and a System Role get View only, and the role picker disables a role the caller could not grant, with a hint. That is T3's second half; the API exposes `withinReach` per user row and `grantable` per role option so the web does not restate the rule.

**Answer (2026-10-17):** show read-only, as recommended. T3 carries the View-only rows and the disabled picker options.

### Q5. Must a user hold at least one role?

Legacy required at least one role (U6). The new form allows none, while the import flags a live role-less user as an error.

**Recommendation:** **yes, as legacy:** create and a role-replacing update need at least one role, in the schema and the form; the import's exemption for Suspended and Trashed users stays, since it describes old data rather than what an admin may save. T5 carries it with the inactive-role rule.

**Answer (2026-10-17):** yes, at least one, as recommended. T5 carries it; the import's exemption stays.

### Q6. Avatar upload now, or keep the link field?

Legacy uploaded avatars to the local public disk, cropped 1:1 to 200×200, 5 MB (U4, F1). VMB has no object storage yet; the admin form takes a URL and otherwise draws a generated avatar.

**Recommendation:** build it as **T7e on Cloudflare R2** (one bucket, served through the API or a public custom domain, 1:1 crop in the browser, 5 MB), shaped as the first file-upload seam so the business modules' documents (invoices, procurement files) reuse it. Sequence it after T7a; until then the generated avatar stands in. If the owner would rather wait for the first business-module upload, T7e is filed but blocked on it.

**Answer (2026-10-17):** build it on R2 after the profile page, as recommended. T7e, sequenced after T7a, with an ADR for object storage.

### Q7. May a person change their own email?

Legacy allowed it on the profile with no re-verification (F1). Here the email is what proves inbox control at activation (ADR-0033) and what the import's checksums key on.

**Recommendation:** **not on the profile for now.** Name, phone and avatar are self-service; the email is changed by an admin in Master, which already dual-writes the identity. Better Auth's `changeEmail` with verification can come later if asked. T7a states this.

**Answer (2026-10-17):** admin-only for now, as recommended. T7a shows the email read-only.

### Q8. What happens to #6?

**Recommendation:** keep #6 open as the parent of the entity-screen gaps (T2, T4, T5, T6) and close it when they close; put the RBAC gaps (T1, T3) under #8, which stays the RBAC parent; open a new parent "Master: profile and account" for T7a–T7e and move #115 under it. #6's own acceptance criteria are met today; it stays open only because it is the natural home for four small tickets, not because its scope is unfinished.

**Answer (2026-10-17):** keep #6 as the parent of the small gaps, as recommended. #8 takes T1 and T3; a new parent takes the profile tickets and #115.

## 13. Dependencies for the business modules

Master rules that exist to serve Trucking, Warehouse and Expense, recorded here so those modules' tickets quote them rather than rediscover them:

- **Division scope** (`UserDivisionFilterScope`, P9): Warehouse items, procurement requests and stock requisitions filter by the caller's division unless they hold `<resource>.all_division`. The new source of divisions is `getAccess().divisions` from the caller's active roles. Two rules differ between legacy branches and must be chosen with #350: a caller with **no** division-scoped role sees **nothing** on `development` and **everything** on `revamp`; and a caller with several divisions sees all of them at once (`revamp`) or works in one at a time (#350's question).
- **`master-divisions.manager`** (P2): legacy's approval steps ask `can('manager', Division::class)` in Orders, Procurement Requests and Stock Requisitions. Here it means "a role scoped to that division that holds `master-divisions.manager`". The key is catalogued and imported; nothing checks it until those modules do.
- **Division names in authorization** (P10): 58 legacy call sites compare `division.name` to `Finance`, `Operations`, `Trucking`, `Executive`. Each becomes a permission check or a division-scope check when its module is built; never a name.
- **Executive dashboards**: four Trucking widgets show only to the Executive division or the super admin. Revamp made Executive an unscoped role with `all_division` grants; the import carries whatever production holds.
- **Unmapped legacy permissions** (P12): Warehouse, Trucking, dashboard and System Log keys are not catalogued. The import reports them per resource and a re-import carries them once their module adds the keys by migration.

## 14. Can #6 close?
