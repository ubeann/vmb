# TypeScript 6, and a recheck of Effect

Researched on 2026-10-02. Question: the owner's priority is performance and efficient resource use (type-check and build speed, Workers CPU and bundle size, CI minutes). Is a TypeScript 5.9 → 6 migration worth doing now, and what does it buy? Has anything changed for Effect since ADR-0038 (2026-09-29)? Builds on `docs/research/vite-plus-and-oxlint.md` (Vite+, Oxlint, Oxfmt) and `docs/research/effect-knip-alchemy.md` §2 without redoing them.

Primary sources only: the TypeScript blog, the microsoft/TypeScript, sveltejs/language-tools, typescript-eslint, Effect-TS and sveltekit-superforms repos, official docs, npm registry metadata (`npm view`, run on this date), and this repo's files and CI logs. A claim that a source doesn't settle is marked **unverified**. `node_modules` isn't installed in this worktree and the brief was read-only, so **nothing was measured locally**. Timings come from CI logs.

## TL;DR

- **TS 6 is a bridge release, not a speed release.** 6.0 (2026-03-23) is "the last release based on the current JavaScript codebase". TS 7.0, the Go port, went GA on 2026-07-08 and is npm `latest` (7.0.2). The latest 6.x is 6.0.3 ([6.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/), [7.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), [npm](https://registry.npmjs.org/typescript)). Neither 6.0 post claims 6.0 checks faster than 5.9. Its one documented speed lever, setting `types` explicitly, is already in place in three of this repo's four tsconfigs.
- **TS 6 costs this repo almost nothing.** No tsconfig here uses a deprecated or removed option, and every changed default is either set explicitly or harmless (see [the mapping](#breaking-changes-mapped-to-this-repo)). Every TS-aware dependency accepts `^6`: svelte-check, Kit 2.70, svelte2tsx, and typescript-eslint (`<6.1.0`).
- **Its value is what it unlocks:**
  - It is the `typescript` that svelte-check's `--tsgo` mode and typescript-eslint keep running alongside TS 7 ([svelte-check README](https://github.com/sveltejs/language-tools/blob/master/packages/svelte-check/README.md), [typescript-eslint #12518](https://github.com/typescript-eslint/typescript-eslint/issues/12518)).
  - It is required by SvelteKit 3.0.0, which went `latest` yesterday: its peer is `typescript ^6.0.0` ([npm](https://registry.npmjs.org/@sveltejs/kit/3.0.0)).
  - It is the check that code is ready for 7.0: 7.0 matches 6.0's checking once code compiles with `stableTypeOrdering` on and no deprecated flags ([7.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)).
- **The real speed-up is TS 7, and here it is small.**
  - Microsoft reports 7.7–11.9× faster builds on large projects ([7.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)).
  - In this repo, `tsc` (api, db, types) is usually a turbo cache hit, and it is never on CI's critical path. That path is the Vitest suites: `@vmb/db:test` takes 199 s on a full miss.
  - TS 7 can run `tsc --noEmit` for api/db/types today, through Microsoft's side-by-side alias.
  - svelte-check's `--tsgo` exists, but has an open bug that reports a crashed check as "0 errors" ([#3127](https://github.com/sveltejs/language-tools/issues/3127)). It is not fit for the CI gate yet.
- **Runtime output does not change.** Vite transpiles with Oxc and Wrangler bundles with esbuild. Neither runs `tsc`, so no TS version changes Workers CPU, bundle size or cold start ([Vite](https://vite.dev/guide/features), [Wrangler](https://developers.cloudflare.com/workers/wrangler/bundling/)).
- **Effect: one of ADR-0038's three triggers fired, the other two did not, so the ADR stands.**
  - Fired: `effect@4.0.0` became npm `latest` on 2026-10-01.
  - Not fired: Superforms 2.31.0 and 3.0.0-next.1 still peer `effect ^3.21.0`, and its adapter still imports v3 APIs.
  - Not fired: no retry, bulk or fan-out need has appeared in the code since 2026-09-29.
  - Effect is not a performance tool. It adds a runtime of about 6–7 KB gz (about 15 KB with Schema) and wraps work in fibers. It removes no CPU work ([MIGRATION.md](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md), [4.0 post](https://effect.website/blog/releases/effect/40), [myths](https://effect.website/docs/additional-resources/myths/)).
- **Recommendation:**
  1. Move to TS 6.0.3 now, as one small PR, and stop Dependabot's failing TS 7 PR (#38).
  2. Optionally run TS 7 `tsc` on api/db/types through the alias. Measure it before keeping it.
  3. Keep `svelte-check` on TS 6 in CI until `--tsgo` is trustworthy.
  4. Leave Effect off this path entirely.

## TypeScript 6 findings

### Role and status

- **6.0.** Released 2026-03-23. "TypeScript 6.0 acts as the bridge between TypeScript 5.9 and 7.0" and is "the last release based on the current JavaScript codebase" ([6.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)). Patches: 6.0.2 (2026-03-23) and 6.0.3 (2026-04-16). No 6.1 has been published, and npm `next` is `7.1.0-dev` ([npm](https://registry.npmjs.org/typescript)). **Unverified:** whether any 6.1 will ship. Neither post says.
- **7.0.** Released 2026-07-08 as the Go-native compiler, and npm `latest` is 7.0.2.
  - "TypeScript 7.0 does not ship with an API." Microsoft expects "TypeScript 7.1 to ship with a new (and different) API".
  - Tools that embed TypeScript, Svelte named among them, "can only currently rely on TypeScript 6.0".
  - The package's `"."` export is only `lib/version.cjs`. That is why API consumers crash on it (npm `exports` of typescript@7.0.2; [language-tools #3063](https://github.com/sveltejs/language-tools/issues/3063)).
- **Side by side.** Microsoft's documented pattern installs `"typescript": "npm:@typescript/typescript6@^6.0.2"` (bin `tsc6`) together with `"@typescript/native": "npm:typescript@^7.0.2"` (bin `tsc`), "so tools like typescript-eslint continue to rely on 6.0" ([7.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). Note that `@typescript/typescript6` is at 6.0.2, one patch behind `typescript@6.0.3` ([npm](https://registry.npmjs.org/@typescript/typescript6)).
- **`@typescript/native-preview` (tsgo).** Its last publish was 2026-07-07 (`7.0.0-dev.20260707.2`). TS 7 GA supersedes it as a way to get the Go compiler. svelte-check still imports its `unstable/*` API typings in source ([`tsgo.ts`](https://github.com/sveltejs/language-tools/blob/master/packages/svelte-check/src/tsgo.ts)).

### Performance reality

- **TS 6 vs 5.9: no documented speed change.** Neither 6.0 post compares checking speed, and 6.0 is the same JavaScript codebase. The one lever both posts give is `types`: "improved their build time anywhere from 20-50% just by setting `types` appropriately". api, web and db already set it. `packages/types`, 9 files and finished at +8.2 s on a full miss, is the only one that would pick up the new default. **Not measured here.**
- **TS 7 is where the speed is.** Microsoft's numbers: 7.7–11.9× faster full builds and 6–26% less memory. A new `--checkers` flag (default 4) parallelises checking ([7.0 post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). These are large codebases (VS Code, Sentry, Playwright). This repo's programs are small, and their cost is mostly the dependency `.d.ts` they pull in: drizzle, better-auth, hono, workers-types. **Unverified:** the speed-up at this size.
- **Where tsgo could run today:**
  - **api, db, types (`tsc --noEmit`): yes.** TS 7.0.2 is GA, and these tsconfigs use nothing 7.0 removed.
    - Blocker: typescript-eslint loads `typescript` for every package's lint, so TS 6 must stay installed under the name `typescript`. Microsoft's alias pattern above does exactly this, and `tsc` then resolves to 7.
    - Dependabot PR #38 shows the failure mode without the alias: lint crashes before `tsc` even reports ([run 36823283812](https://github.com/ubeann/vmb/actions/runs/36823283812)).
    - **Unverified:** how pnpm checks Kit's and svelte-check's `typescript` peer against an `npm:@typescript/typescript6` alias, and whether Dependabot updates aliased specs.
  - **web (svelte-check): only with `--tsgo` / `--tsgo-experimental-api`,** and only with TS 6 also installed. svelte-check 4.7.6 already finds TS 7 under the `@typescript/native` alias ([#3073](https://github.com/sveltejs/language-tools/pull/3073), released 2026-07-27).
    - Documented limits: "anything that is not in the root dir of your tsconfig.json and is a Svelte file will not be properly loaded and type-checked", and "might result in slightly different type check outcomes" ([README](https://github.com/sveltejs/language-tools/blob/master/packages/svelte-check/README.md)).
    - Open bugs: `--tsgo` reports "0 errors" and exits 0 when the compiler process is killed ([#3127](https://github.com/sveltejs/language-tools/issues/3127)). It also checks extra files ([#3120](https://github.com/sveltejs/language-tools/issues/3120)).
    - #3127 alone rules it out as the CI gate: on a 2 vCPU / 8 GB runner, an OOM kill would turn the gate green.
    - Only the type-check step moves to Go. svelte2tsx still converts components in JS. **Unverified:** the net speed-up. The maintainer gives no figure beyond "slightly faster" than the experimental-API mode ([#3063 comment](https://github.com/sveltejs/language-tools/issues/3063)).
- **svelte-check's TS 7 plan.** A "content mapper" integration is "close to ready" ([#3063](https://github.com/sveltejs/language-tools/issues/3063), PR [#3111](https://github.com/sveltejs/language-tools/pull/3111) open), built on tsgo's content-mapper support. It will "still require both TypeScript 6 and 7". Dropping TS 6 entirely waits on the TS 7.1 API and on typescript-eslint ([#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)).
- **What it would save in CI.** Typecheck tasks are turbo-cached on most runs and finish before the critical path on every sampled run (table above). TS 7 would cut their CPU, which on 2 vCPU frees time for the Vitest suites. **Unverified:** how many wall-clock seconds that is. The run is bounded by `@vmb/db:test` (199 s, PGlite) or `@vmb/web:test` (browser mode). Most of the gain would be local: `pnpm typecheck` and pre-push feedback.
- **Runtime output: unchanged.**
  - "Vite only performs transpilation on `.ts` files and does **NOT** perform type checking". It uses the Oxc transformer and reads only a handful of tsconfig fields (`verbatimModuleSyntax`, `jsx*`, `experimentalDecorators`, …) ([Vite features](https://vite.dev/guide/features)).
  - Wrangler bundles the API Worker with esbuild ([bundling](https://developers.cloudflare.com/workers/wrangler/bundling/)).
  - The TS migration changes none of those fields. The deployed Worker (3,375 KiB, 594 KiB gzip, startup 92 ms in [run 36958377197](https://github.com/ubeann/vmb/actions/runs/36958377197)) would not change.

## Effect recheck

### "Code efficiency": two different things

- **(a) Runtime efficiency on Workers. Effect costs here; it doesn't save.**
  - **Bundle.** A minimal Effect 4 program is "~6.3 KB (minified + gzipped). With Schema, ~15 KB" ([MIGRATION.md](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md)). The 4.0 post gives 7.1 kB, against 35.6 kB for 3.x ([4.0 post](https://effect.website/blog/releases/effect/40)). Against today's 594 KiB gzip Worker, that is about 1–2.5% more, far under the 64 MiB limit. Startup time is a hard 1 s limit, and "larger bundles … increase startup time" ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
  - **CPU.** Effect runs your code inside fibers. Its own docs concede per-operation overhead and argue it vanishes at application level, because Effect coordinates "thunks of code" ([myths](https://effect.website/docs/additional-resources/myths/)). The 4.0 throughput and memory gains (6.4× tasks/s, 86% less heap per fiber) are gains **over Effect 3**, not over plain Promises ([4.0 post](https://effect.website/blog/releases/effect/40)).
  - No source claims Effect lowers CPU per request against async/await. This repo's hot paths are Neon HTTP queries and Better Auth hashing. Wrapping them in `Effect.tryPromise` adds work and removes none. **Unverified:** CPU per request on Workers, still unmeasured, as ADR-0038 noted.
- **(b) Developer efficiency. This is real and unchanged.** It covers typed errors (the store's `Promise<T>` hides `MasterNotFoundError`/`MasterConflictError`), retries and timeouts, and DI through Layers (`effect-knip-alchemy.md` §2).

## Recommendation

1. **Do step 0 now.** It is a small, reversible PR: bump `typescript` to `^6.0.3` in the six manifests and run the gate. Close PR #38, then add a Dependabot `ignore` for `typescript` `>=7` so it doesn't come back red every week (`.github/dependabot.yml:19-29`). Record it as a short ADR or an ARCHITECTURE note, because it sets the TS policy until 7.1. Expect no measurable speed change.
2. **Treat step 1 as an experiment, not a migration.** Before keeping it, time `tsc --noEmit` for api, db and types under 6.0.3 and 7.0.2 (`time pnpm --filter @vmb/api typecheck`, three runs each). Keep it only if the local gain is worth the aliasing.
3. **Keep `svelte-check` on TS 6 in CI.** Revisit `--tsgo` when #3127 is fixed and the content-mapper PR ships. Trying it locally is fine.
4. **Effect stays not adopted.** For "code efficiency" in the performance sense it moves the wrong way. For the one live reliability gap, background email with no retry, a plain bounded retry with `AbortSignal.timeout` in `sendEmail` is the proportional fix.

## Open questions

- Is a TS 6 bump worth a PR on its own, given it buys no speed? Its value lies in steps 1–2 and Kit 3.
- Do you want the TS 7 alias setup (two `typescript` packages in each manifest) for a gain that mostly shows up locally?
- Should ADR-0038 get a dated note that trigger 1 fired, or wait until a second trigger moves?
- Does background email failing without a retry (since #247) matter enough to fix now, outside any Effect decision?
