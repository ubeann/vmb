# Vite+ and Oxlint for this repo

Researched on 2026-09-30. Question: should this repo adopt **Vite+** and/or **Oxlint**? What does each offer, how well does it fit the current toolchain, what would migration cost, and what would it actually improve here?

Primary sources only: viteplus.dev, oxc.rs, voidzero.dev, the projects' GitHub repos and source, npm registry metadata, the official docs of the tools involved, and this repo's own files. A claim that a source doesn't settle is marked **unverified**.

## TL;DR

- **Vite+ 1.0 is GA, MIT-licensed and free, but it came out two days ago** (2026-09-28). There are no paid tiers, and VoidZero's move to Cloudflare keeps it MIT ([release](https://github.com/voidzero-dev/vite-plus/releases/tag/v1.0.0), [announcement](https://voidzero.dev/posts/announcing-vite-plus-1-0), [Cloudflare post](https://voidzero.dev/posts/voidzero-cloudflare)).
- **Replacing Turborepo with Vite+ would be a step backwards today.** Vite Task has no remote cache yet; that is "planned for future versions" ([announcement](https://voidzero.dev/posts/announcing-vite-plus-1-0)). Its GitHub Actions cache reuse is marked experimental ([docs](https://viteplus.dev/guide/github-actions-cache)). ADR-0023's affordable docs-only PR gate depends on Turborepo's remote cache replaying code tasks.
- **Oxlint cannot lint Svelte templates.** It reads only the `<script>` blocks of `.svelte` files ([compatibility](https://oxc.rs/compatibility)). It skips `no-unused-vars` in `.svelte` files entirely ([rule doc](https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-unused-vars)). JS plugins cannot load custom parsers such as Svelte's ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins)). So `eslint-plugin-svelte` stays for as long as `apps/web` needs its 37 recommended rules, including the `svelte/no-navigation-without-resolve` rule the repo configures.
- **Type-aware Oxlint (tsgolint) is stable, but it targets TypeScript 7** ([type-aware](https://oxc.rs/docs/guide/usage/linter/type-aware), [blog](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). This repo resolves `typescript@5.9.3`, and `svelte-check`/`@sveltejs/kit` peer on TS `^5 || ^6`. Type-aware rules also do not cover `.svelte` files ([RFC #21936](https://github.com/oxc-project/oxc/discussions/21936)).
- **Oxfmt could replace Prettier and both of its plugins.** It lists Svelte as "Full Support" once `svelte` is installed, and it has built-in Tailwind class sorting ([compatibility](https://oxc.rs/compatibility), [config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference)). But it is still beta (0.71), and `.svelte` and `.md` files go through a bundled Prettier, not the fast native path ([language support](https://oxc.rs/docs/guide/usage/formatter/language-support)).
- **Lint is not the bottleneck here.** In a measured master CI run, `prettier --check .` took 9.1 s and web ESLint finished about 10 s into a 57 s Turborepo run. The critical path was `svelte-check` and the Vitest browser suite (see [Current toolchain](#current-toolchain)).
- **Recommendation:** don't adopt Vite+ now. If you want faster hooks and a smaller lint config, trial Oxlint in hybrid mode: Oxlint everywhere, with ESLint kept only for `.svelte` and `.svelte.ts` files. Keep Prettier until Oxfmt reaches 1.0. See [Recommendation](#recommendation).

## Vite+ findings

**What it is.** Vite+ is a "unified toolchain": one `vite-plus` package with a `vp` CLI. It bundles Vite, Rolldown, Vitest, Oxlint, Oxfmt, tsdown and the Vite Task runner ([getting started](https://viteplus.dev/guide/), [why](https://viteplus.dev/guide/why)).

- **Commands:** `vp dev/build/preview` (Vite), `vp check` (Oxfmt + Oxlint + tsgolint type check), `vp lint`, `vp fmt`, `vp test` (Vitest), `vp pack` (tsdown), `vp run` (cached, workspace-aware tasks), `vp staged`/`vp hooks` (git hooks), and package-manager wrappers (`vp install/add/...`).
- **Global-CLI-only commands:** `vp env` for Node and package-manager management, plus `vp upgrade` and `vp implode` ([local CLI](https://viteplus.dev/guide/local-cli), [env](https://viteplus.dev/guide/env)).
- **Bundled versions in 1.0.0:** Vite 8.3.1, Rolldown 1.2.11, Vitest 5.0.1, Oxlint 1.85.0, oxlint-tsgolint 7.0.2003, Oxfmt 0.70.0, tsdown 0.23.0 ([release notes](https://github.com/voidzero-dev/vite-plus/releases/tag/v1.0.0)).
- **Requirement:** Node `^22.18.0 || ^24.11.0 || >=26.0.0` ([npm metadata](https://registry.npmjs.org/vite-plus)).

**License and commercial terms.**

- MIT, per npm and the GitHub license ([npm](https://registry.npmjs.org/vite-plus), [repo](https://github.com/voidzero-dev/vite-plus)).
- The alpha announcement says VoidZero had "considered a paid license for companies" but chose to make it "truly free and open source". It points to its separate commercial product, Void ([alpha post, 2026-03-13](https://voidzero.dev/posts/announcing-vite-plus-alpha)).
- VoidZero is joining Cloudflare, and "Vite, Vitest, Rolldown, Oxc, and Vite+ will remain open-source and MIT-licensed" ([2026-06-04](https://voidzero.dev/posts/voidzero-cloudflare)).
- The 1.0 announcement mentions no paid tiers ([1.0 post](https://voidzero.dev/posts/announcing-vite-plus-1-0)).

**Maturity.**

- Timeline: alpha on 2026-03-13, beta on 2026-07-02, rc.0 on 2026-09-22, and 1.0.0 on 2026-09-28, which promoted rc.1 "with no code changes" ([voidzero blog](https://voidzero.dev/blog), [releases](https://github.com/voidzero-dev/vite-plus/releases)).
- Stable in 1.0: `create/install/dev/check/test/build/pack/run/env`, `setup-vp`, and git hooks.
- Not there yet: "remote caching, deeper monorepo diagnostics, `vp release`, and `vp docs` are planned" ([1.0 post](https://voidzero.dev/posts/announcing-vite-plus-1-0)).
- Open follow-ups exist for real-world `vp migrate` runs, including bad `packageManager` pins ([#2037](https://github.com/voidzero-dev/vite-plus/issues/2037)).

**SvelteKit compatibility.**

- Vite+ says it integrates with "React, Vue, Svelte, and others" ([why](https://viteplus.dev/guide/why)) and ships `vp create svelte` ([create](https://viteplus.dev/guide/create), [#869](https://github.com/voidzero-dev/vite-plus/issues/869)).
- A fixed bug shows SvelteKit running inside a Vite+ monorepo: the Oxc LSP loaded `vite.config.ts` and fired the `sveltekit()` hooks, which created a stray `.svelte-kit` ([#1756](https://github.com/voidzero-dev/vite-plus/issues/1756)). That class of problem is why `lazyPlugins` exists ([troubleshooting](https://viteplus.dev/guide/troubleshooting)).
- `vite-plus-core` 1.0.0 bundles Vite 8.3.1 ([npm](https://registry.npmjs.org/@voidzero-dev/vite-plus-core/latest)), and `@sveltejs/kit` peers `vite ^8.0.0` ([npm](https://registry.npmjs.org/@sveltejs/kit/latest)).
- **Unverified:** that `@sveltejs/kit` + `adapter-cloudflare` builds identically under the `vite-plus-core` alias. No SvelteKit app appears in Vite+'s ecosystem CI list ([repo.json](https://github.com/voidzero-dev/vite-plus/blob/main/ecosystem-ci/repo.json)).

**Cloudflare Workers.** `apps/api` doesn't use Vite at all: `wrangler dev`/`wrangler deploy` bundle it from source. Vite+ therefore offers the API nothing beyond `vp test` and `vp lint`. `@cloudflare/vite-plugin` isn't used anywhere in the repo, so nothing there is at stake.

**Incremental adoption.**

- `vp lint`, `vp fmt` and `vp test` work from the project-local package without the global CLI ([local CLI](https://viteplus.dev/guide/local-cli)), and `vp check` can skip steps (`check.fmt: false`) ([check](https://viteplus.dev/guide/check)). You could keep Turborepo and call `vp lint`/`vp fmt` from turbo tasks.
- But `vp migrate` only runs on the **workspace root**: "Vite+ cannot migrate one workspace member" ([migrate](https://viteplus.dev/guide/migrate)).
- Its automatic ESLint migration runs `@oxlint/migrate` only "if there's an eslint config at root" ([source](https://github.com/voidzero-dev/vite-plus/blob/main/packages/cli/src/migration/migrator/eslint.ts)). This repo keeps its ESLint configs per package, so expect a hand port.
- The manual-install docs still require the `vite`/`vitest` overrides ([local CLI](https://viteplus.dev/guide/local-cli)). **Unverified:** whether lint/fmt-only use truly needs them.
- In practice, "Vite+ for lint and format only" gives you standalone `oxlint` + `oxfmt` with extra coupling to the Vite/Vitest versions.

## Oxlint findings

**Status and versions.** Oxlint 1.0 went stable on 2025-06-10 ([blog](https://oxc.rs/blog/2025-06-10-oxlint-stable)). The latest is 1.86.0, MIT ([npm](https://registry.npmjs.org/oxlint)). It follows semver, **except** nursery rules, JS plugins and type-aware linting, which "may introduce breaking changes at any time" ([versioning](https://oxc.rs/docs/guide/usage/linter/versioning)).

**Rule coverage.** "More than 800 rules from ESLint core and various popular plugins" ([migrate from ESLint](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint)). The built-in plugins are eslint, typescript, unicorn, oxc (on by default), plus react, react-perf, nextjs, import, jsdoc, jsx-a11y, node, promise, jest, vitest and vue ([plugins](https://oxc.rs/docs/guide/usage/linter/plugins)). Counted from the docs index ([llms.txt](https://oxc.rs/llms.txt)): eslint 187, typescript 110, unicorn 138, vitest 73, import 33, jsx-a11y 36. There is **no Svelte plugin**. Status is tracked in [#481](https://github.com/oxc-project/oxc/issues/481).

**Svelte support.** This is the deciding factor for `apps/web`.

- `.svelte` files are linted "by linting only their `<script>` blocks" ([linter](https://oxc.rs/docs/guide/usage/linter)). The compatibility matrix rates Svelte and SvelteKit **Partial: "No template linting yet"** ([compatibility](https://oxc.rs/compatibility)).
- Because Oxlint can't see template usage, `no-unused-vars` "ignores `.d.ts`, `.astro`, `.svelte` and `.vue` files entirely" ([rule doc](https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-unused-vars), [#17991](https://github.com/oxc-project/oxc/issues/17991)). The same limitation caused `bind:this` false positives in `prefer-const` ([#19470](https://github.com/oxc-project/oxc/issues/19470)) and `no-unassigned-vars` ([#26038](https://github.com/oxc-project/oxc/issues/26038)).
- JS plugins "Not supported yet: Custom file formats and parsers (e.g. Svelte, Vue, Angular)" ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins)). The missing `languageOptions.parser` API "has been said to block Svelte community from migrating" ([#20373](https://github.com/oxc-project/oxc/issues/20373)).
- The fix is "language plugins" (RFC opened 2026-04-29, tracking issue opened 2026-06-10, both still open). The RFC also says framework files get no type checking today ([RFC #21936](https://github.com/oxc-project/oxc/discussions/21936), [#23207](https://github.com/oxc-project/oxc/issues/23207)).
- **What you'd lose vs `eslint-plugin-svelte`:** all 37 rules in its `recommended` config ([v3.23.0 `lib/configs/flat/recommended.js`](https://www.npmjs.com/package/eslint-plugin-svelte/v/3.23.0), [rules list](https://sveltejs.github.io/eslint-plugin-svelte/rules/)). These include template checks such as `svelte/no-at-html-tags` (XSS), `svelte/require-each-key`, `svelte/valid-each-key`, `svelte/no-unused-props`, `svelte/no-navigation-without-resolve`, `svelte/prefer-svelte-reactivity` and `svelte/no-dom-manipulating`, plus accurate unused-variable detection across 116 components.
- Svelte's own CLI offers only `eslint` and `prettier` add-ons. The Svelte docs don't mention Oxlint or Oxfmt ([svelte.dev llms-full.txt](https://svelte.dev/llms-full.txt), sections `eslint`/`prettier`).

**Type-aware linting (tsgolint).**

- Declared stable on 2026-07-22 with 59 of typescript-eslint's 61 type-aware rules ([blog](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable), [tsgolint README](https://github.com/oxc-project/tsgolint)).
- `--type-check` can replace `tsc --noEmit` ([type-aware](https://oxc.rs/docs/guide/usage/linter/type-aware)).
- Requirements: "TypeScript **7.0+** is required", with no `baseUrl` and no options that TS 6/7 deprecated or removed. Only the root config can enable it ([type-aware](https://oxc.rs/docs/guide/usage/linter/type-aware)).
- Readme speed figures: 12 to 18x vs ESLint + typescript-eslint on vscode, typescript, typeorm and vuejs/core ([tsgolint README](https://github.com/oxc-project/tsgolint)).
- Fit here:
  - The repo **doesn't use type-aware rules today** (`tseslint.configs.recommended`, not `recommendedTypeChecked`), so this would be a new capability, not a replacement.
  - The repo resolves `typescript@5.9.3` (`pnpm-lock.yaml`). TS 7.0.2 is npm `latest` ([npm](https://registry.npmjs.org/typescript)). `svelte-check` 4.7.6 and `@sveltejs/kit` 2.70.3 peer TS `^5 || ^6`, and `typescript-eslint` 8.71 peers `<6.1.0` ([svelte-check](https://registry.npmjs.org/svelte-check/latest), [kit](https://registry.npmjs.org/@sveltejs/kit/latest), [typescript-eslint](https://registry.npmjs.org/typescript-eslint/latest)).
  - **Unverified:** whether tsgolint (it embeds typescript-go) works while the project's own `typescript` stays on 5.9. The docs state the TS 7 requirement but don't say whether it means the installed package or tsconfig semantics.

**JS plugins.** Status is **alpha**. The API is "compatible with ESLint v9+", with conformance-tested plugins such as regexp, sonarjs, playwright and `@stylistic` ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins), [linter](https://oxc.rs/docs/guide/usage/linter)).

**Config.** Oxlint reads `.oxlintrc.json`/`.jsonc` or `oxlint.config.ts`/`.mts`, discovers nested configs (nearest file wins, no auto-merge, `extends` to share a base), and respects `.gitignore` ([config](https://oxc.rs/docs/guide/usage/linter/config), [nested config](https://oxc.rs/docs/guide/usage/linter/nested-config), [migrate](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint)). It honours `eslint-disable*` comments as well as `oxlint-disable*` ([ignore comments](https://oxc.rs/docs/guide/usage/linter/ignore-comments)). That covers the two in `apps/web/src/lib/utils.ts`.

**Migration tooling.** `npx @oxlint/migrate [flat-config]` converts rules, severities, options, overrides, globals and ignores. It supports `--type-aware` and carries unsupported plugins over as JS plugins by default ([migrate](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint)). Latest is 1.86.0 ([npm](https://registry.npmjs.org/@oxlint/migrate)). **Not run here** (no installs), so exact rule parity for this repo's configs is unverified.

**Running Oxlint and ESLint together.** The documented pattern is `oxlint && eslint`, with `eslint-plugin-oxlint` placed last in the flat config to turn off the ESLint rules Oxlint already covers. `oxlint.buildFromOxlintConfigFile('./.oxlintrc.json')` derives that list from your Oxlint config ([migrate](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint), [eslint-plugin-oxlint README](https://github.com/oxc-project/eslint-plugin-oxlint)). `eslint-plugin-oxlint` peers `oxlint ~1.86.0`, so the two must be bumped together ([npm](https://registry.npmjs.org/eslint-plugin-oxlint), [versioning](https://oxc.rs/docs/guide/usage/linter/versioning)).

**Performance claims, as stated by the sources.** These are the vendor's own figures, not measured here:

- "50 to 100 times faster than ESLint", depending on CPU cores ([linter](https://oxc.rs/docs/guide/usage/linter), [benchmarks](https://oxc.rs/docs/guide/benchmarks), [bench-javascript-linter](https://github.com/oxc-project/bench-javascript-linter)).
- About 10,000 files per second on real repos ([1.0 blog](https://oxc.rs/blog/2025-06-10-oxlint-stable)).

## Oxfmt (short)

- **Status:** beta since 2026-02-24 ([blog](https://oxc.rs/blog/2026-02-24-oxfmt-beta)), latest 0.71.0 ([npm](https://registry.npmjs.org/oxfmt)). A 1.0 milestone is referenced ("Planned for Oxfmt 1.0", [compatibility](https://oxc.rs/compatibility)).
- **Prettier parity:** it "passes 100% of Prettier's JavaScript and TypeScript conformance tests". Differences are treated as bugs, and its output is closest to Prettier 3.8 ([formatter](https://oxc.rs/docs/guide/usage/formatter), [migrate](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier)).
- **Speed claims:** "approximately 30x faster than Prettier" ([formatter](https://oxc.rs/docs/guide/usage/formatter)) and "35x" ([benchmarks](https://oxc.rs/docs/guide/benchmarks)). The two pages disagree slightly.
- **Svelte:**
  - The matrix rates Svelte and SvelteKit **Full Support: "Requires installing `svelte/compiler` separately"** ([compatibility](https://oxc.rs/compatibility)).
  - `.svelte` is **Prettier-backed**: it runs a bundled `prettier-plugin-svelte`, enabled with the `svelte` option. The `svelte` package must already be installed, which `apps/web` has ([config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference), [language support](https://oxc.rs/docs/guide/usage/formatter/language-support), [#19715](https://github.com/oxc-project/oxc/issues/19715)).
  - Script blocks inside `.svelte` go through the native formatter ([language support](https://oxc.rs/docs/guide/usage/formatter/language-support)).
  - Markdown is also Prettier-backed, so the 56 `.md` files and 116 `.svelte` files would not see native-Rust speed.
- **Tailwind:** built-in `sortTailwindcss` uses "the same algorithm as prettier-plugin-tailwindcss", including in Svelte and in templates. `functions: ["cn"]` sorting is supported, but regexes are not ([sorting](https://oxc.rs/docs/guide/usage/formatter/sorting), [config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference)).
- **Differences that would cause a first-run diff:**
  - `sortPackageJson` is **on by default**, so `package.json` key order would change.
  - TOML is formatted natively, and Prettier doesn't format TOML here today, so `.mise.toml`, `fnox.toml` and `wrangler.toml` would change.
  - The default `trailingComma` is `"all"`, but `oxfmt --migrate prettier` carries the repo's `"none"` across.
  - `printWidth` defaults to 100 in both.
  - Sources: [config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference), [unsupported features](https://oxc.rs/docs/guide/usage/formatter/unsupported-features).
- `.prettierignore` is honoured globally ([ignore files](https://oxc.rs/docs/guide/usage/formatter/ignore-files)).
- **Side finding:** for Tailwind v4, `prettier-plugin-tailwindcss` says "you must specify your CSS file entry point" via `tailwindStylesheet` ([README](https://github.com/tailwindlabs/prettier-plugin-tailwindcss)). `packages/config/prettier.config.js` doesn't set it. Oxfmt's equivalent `stylesheet` defaults to Tailwind's own `theme.css`. **Unverified:** how this affects the order of this repo's custom token utilities today.

**What would get faster.**

- The lefthook `eslint` pre-commit step: each commit currently cold-starts ESLint with the typescript-eslint and svelte parsers once per touched package.
- The `Format` CI step, but only on a turbo cache miss.
- The CI `lint` task is already off the critical path, so wall-clock savings there are near zero.

**What would break or need care.** In the hybrid, `scripts/lint-staged-eslint.sh` must keep working for web `.svelte` files. `.vscode/extensions.json` would gain `oxc.oxc-vscode`. `AGENTS.md`/docs mention ESLint and Prettier.

**ADRs.**

- **Replacing Turborepo** supersedes ADR-0008. It regresses ADR-0023, whose "docs-only PR is affordable because turbo replays its code tasks from the remote cache" rationale would lose its remote cache. It also touches ADR-0010/0021 if the global `vp env` manages Node and pnpm. This needs a new ADR.
- **Oxlint or Oxfmt as npm devDependencies** stay inside Dependabot's npm ecosystem (ADR-0021) and need no mise pin. A short ADR recording "Oxlint primary, ESLint only for Svelte" is advisable, because it changes a documented convention (`@vmb/config` ships the shared ESLint config).
- **Lefthook stays:** Vite+ won't auto-migrate it anyway ([migrate](https://viteplus.dev/guide/migrate)).
- **CI gate unchanged:** the same `turbo lint` / `format:check` task names can keep pointing at new commands, so ADR-0023's "PR runs what master runs" still holds.

## Recommendation

1. **Do not adopt Vite+ now.** Its main draw for a Turborepo repo, a single task runner with caching, lacks the remote cache this repo's CI gate relies on. Its lint and format pieces are available standalone without the Vite/Vitest override coupling. Revisit when (i) Vite Task ships remote caching and (ii) SvelteKit is known-good under `vite-plus-core`. It would need an ADR superseding 0008.
2. **If you want a change, take option (b): an Oxlint + ESLint hybrid scoped by file type.** It is small and reversible, and it removes ESLint from three of four packages without dropping the Svelte template rules. Measure the pre-commit and `lint` task times before and after; the gain should be felt mainly in hooks. Don't enable type-aware rules until the TypeScript 7 question is settled.
3. **Keep Prettier for now.** Revisit Oxfmt at 1.0, or when its Svelte and Markdown support becomes native, which is where this repo's formatting time goes. If adopted, pair it with `sortPackageJson: false` and a reformat commit listed in `.git-blame-ignore-revs`.
4. **Track Oxlint language plugins** ([#23207](https://github.com/oxc-project/oxc/issues/23207)). When `.svelte` templates become lintable, option (c) becomes viable and ESLint can go entirely.

## Open questions for you

- Is faster pre-commit feedback worth adding a second linter (option b), or is (a) fine given CI lint is already cached and off the critical path?
- Do you want type-aware rules (`no-floating-promises` and similar)? If so, are you willing to move to TypeScript 7 while `svelte-check`, `@sveltejs/kit` and `typescript-eslint` still peer on TS ≤6?
- Should a linter swap get its own ADR (recommended), or just a `docs/ARCHITECTURE.md` note?
- Is a one-time repo-wide reformat acceptable, including `package.json` key order if `sortPackageJson` stays on, and TOML files that Prettier doesn't touch today?
- Separately from this decision: should `tailwindStylesheet` point at `apps/web/src/app.css` in the Prettier config?
