# Squash-merge vs. stacked PRs

Researched on 2026-09-24. Question: does making squash-merge the _default_ merge method conflict with the GitButler-stacked-PR + GitHub-sub-issues workflow this repo wants to adopt?

## Executive summary

**Yes, squash-merge conflicts with stacking — but only for the classic manual/description-based flavor of stacking. The two mitigations the primary sources actually document are: (a) merge the whole stack as one atomic bottom-up operation (GitHub's native stacked-PR merge, and GitButler's is built on top of it), or (b) if merging PR-by-PR, immediately restack/rebase the branches above the one just merged.** This repo's adopted policy below (§ Recommendation, point 4 — "squash only leaves," merge-commit anything with a child stacked on it) is a third option: a bespoke synthesis of (b) plus Graphite's and Git Town's stated reasoning, not one of the two named-and-documented mitigations above, and not something any source publishes as a standard practice in its own right — don't cite it elsewhere as industry-standard. Squashing the bottom PR of a stack replaces its N original commits with a single new commit with a new SHA; any PR still open above it was branched from the _old_ commits, so it will show those old commits' full diff again as "new" changes against the new base — a well-documented phenomenon called a **phantom conflict / phantom diff** (Git Town's term, confirmed independently by GitButler's own bug tracker for exactly this scenario: [gitbutlerapp/gitbutler#15154](https://github.com/gitbutlerapp/gitbutler/issues/15154)). It's not fatal — every stacking tool has a fix — but it is not "clean" by default the way merge-commit or rebase-merge are.

**Recommendation for this repo:** keep squash as the _default_ for standalone/leaf tickets (matches the stated reasoning — small single-ticket PRs are exactly what squash is good for), but do not treat it as unconditional. Concretely:

1. Turn on **"Automatically delete head branches"** in repo settings (currently `false` per `gh api repos/ubeann/vmb`) — GitButler's own docs call this out as the mechanism GitHub uses to retarget the next PR in a description-based stack once the one below it lands.
2. Merge stacked PRs **bottom-up, one layer at a time, restacking (`but` will do this via `but pull` / its own rebase) immediately after each merge** — do not leave a squash-merged bottom PR sitting for a while before dealing with the PRs above it.
3. Check whether this repo is enrolled in GitHub's new native "stacked pull requests" feature (public preview since 2026-07-30). If it is (or once it is), merging the _entire stack_ in one action with squash selected is safe and documented to behave like "one squash commit per PR, applied bottom-up" — GitHub's own reference docs describe this explicitly. That native path removes essentially the entire risk described in the mechanics section below, and is the actual standard mitigation, not a workaround.
4. If not enrolled / not using native stacks, prefer **merge commit or rebase-merge for any PR that currently has children stacked on it**, and reserve squash for the ticket at the _top_ of a stack (or truly standalone tickets) where there's nothing above it to go stale. This is the "squash only leaves" middle ground described below — nobody publishes it as a named policy, but it falls directly out of Graphite's and Git Town's stated reasoning and is the most literal reading of GitButler's own "merge from the bottom upward" instruction for description-based stacks.

## Mechanics: what actually happens when you squash the base of a stack

Take a 3-PR stack: `feature/a` → `feature/b` (based on `a`) → `feature/c` (based on `b`), each with several commits.

1. You squash-merge `feature/a` into `main`. GitHub takes all of `a`'s commits, collapses them into **one new commit** on `main` with a **new SHA** — none of `a`'s original commit objects land on `main`.
2. `feature/b` was branched from the tip of `a`'s original (un-squashed) commits. Those commits still exist in `b`'s history — they were never deleted, just not walked forward. From `main`'s new perspective, `b` now looks like: "all of `a`'s original commits, plus `b`'s own commits" — because `main` no longer contains those SHAs, only their squashed equivalent.
3. Two visible symptoms result:
   - **Phantom diff**: the PR for `b` (and `c`) now appears to include `a`'s entire diff again, even though those changes already landed (just under a different commit). Reviewers see noise they already reviewed.
   - **Phantom conflict**: if `b` or `c` touch the same lines `a` touched, syncing/rebasing tooling (Git, GitButler, Git Town, etc.) can misidentify the still-present old commit vs. the new squash commit as _two independent edits to the same line_ and report a merge conflict that isn't a real disagreement — it's the same change appearing twice under different SHAs. Git Town's docs name this explicitly: _"Git sees the new commit on main and the commit on the shipped branch as conflicting edits to the same line"_ → **"phantom conflicts."** ([git-town.com/stacked-changes.html](https://www.git-town.com/stacked-changes.html), accessed 2026-09-24)
   - GitButler's own issue tracker documents the identical failure mode inside GitButler itself: when a squash-merged stack is pulled back into the local workspace, GitButler's commit-matching logic is 1:1 and can't match GitHub's 1 squash commit against GitButler's N original workspace commits, so it treats the branch as unintegrated, cherry-picks the (already-landed) commits back onto a base that already has them, and produces a synthetic `{conflicted}` commit — a permanent "zombie" branch that never self-clears. ([gitbutlerapp/gitbutler#15154](https://github.com/gitbutlerapp/gitbutler/issues/15154), accessed 2026-09-24 — open issue, no shipped fix as of this date)
4. The standard fix in every tool that supports stacking is the same shape: **replay only the genuinely-new commits of the upper branch onto the new base**, discarding anything already contained in the squash commit. Git natively supports this via `git rebase --onto <new-base> <old-base> <branch>` or `git rebase --fork-point`; Git Town wraps it as `git town sync --stack`; GitButler wraps it as its own rebase-on-pull behavior (`but pull` / automatic restacking in the GUI) — though per #15154 above, GitButler's automatic version currently mishandles the squash case specifically, so a manual `but` intervention or `git rebase --onto` may be needed as a workaround until that's fixed.
5. **This entire problem is specific to squashing one layer while other layers stay open on old commits.** It does not occur if:
   - you merge the whole stack **atomically in one action** (GitHub's native stacked-PR merge does this — see below), because there's no window where an upper PR is diffed against a stale lower branch; or
   - you use **merge commit** or **rebase-merge** instead of squash for the bottom PR, because both preserve the original commit SHAs (merge commit: SHAs unchanged, just wrapped in a merge commit; rebase-merge: commits replayed 1:1 with new SHAs but 1:1, so GitHub/GitButler's usual "already in base" detection still matches on content and the auto-retarget logic isn't fooled by a many-to-one collapse).

## What primary sources recommend

**GitHub — merge methods (general).** GitHub's own docs describe three methods: merge commit ("preserves the full commit history... creates an explicit merge point"), squash ("works best for short-lived branches... if you keep working on the same head branch after a squash merge, later pull requests can include commits that were already squashed into the base branch, which can make merge conflicts more likely" — this is GitHub's own phrasing of exactly the phantom-diff mechanism above, stated for _any_ continued branch work, not specific to stacking), and rebase-and-merge ("resembles a fast-forward merge by maintaining a linear project history"). ([docs.github.com — About merge methods](https://docs.github.com/articles/about-merge-methods-on-github), accessed 2026-09-24)

**GitHub — native stacked pull requests (public preview, shipped 2026-07-30).** This is a genuinely new, directly relevant primary source: GitHub now has a first-party stacked-PR feature (distinct from GitButler's or Graphite's), and it explicitly addresses this exact question:

- _"Stacks support merge commit, squash, and rebase merge methods, and they are merge-queue aware."_
- On merging the whole stack: _"The pull requests below it merge too, and the pull requests above stay open and automatically re-target the stack's base branch."_ And critically: _"The resulting commit history is the same as merging each pull request individually, starting from the bottom."_ ([docs.github.com — About stacked pull requests](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs), accessed 2026-09-24)
- The merge-method reference page spells out squash's behavior for a stack specifically: _"Squash: creates one clean, squashed commit per pull request. Merging `n` pull requests creates `n` squashed commits on the base branch."_ This is the atomic, "handled cleanly" case — GitHub squashes each layer in turn as part of one operation, so no layer is ever left diffed against a stale base. ([docs.github.com — Stacked pull requests reference](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests), accessed 2026-09-24)
- The changelog announcement confirms the same for partial merges: _"the pull requests above it stay open and automatically rebase and retarget."_ ([github.blog/changelog — Stacked pull requests are now in public preview, 2026-07-30](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/), accessed 2026-09-24)
- Caveat page: _"Stacked pull requests require all branches to be in the same repository. Cross-fork stacks are not supported. Stacked pull requests are not supported in GitHub Desktop."_ Also: if merging via the API, the asynchronous merge endpoint must be used to preserve stack behavior. No named tools (GitButler, Graphite) are mentioned as integrating with it in the changelog post itself. ([docs.github.com — About stacked pull requests](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs), accessed 2026-09-24)
- **Note on what "public preview" implies:** the doc states the feature "is in public preview and subject to change" but the fetched pages did not surface an explicit enrollment/opt-in mechanism for a given repository. Whether `ubeann/vmb` is currently enrolled was not verified directly against the GitHub UI/API for this feature flag — see Caveats.

**GitButler — docs.gitbutler.com.** GitButler publishes two supported stacking modes:

- **Native GitHub stacks** (when the repo supports GitHub's native stacked-PR feature above): GitButler detects support and, per its own release notes, "we will properly create a GitHub stack of those branches" when you run `but pr` — deferring merge-mechanics entirely to GitHub's native behavior described above. ([blog.gitbutler.com — GitButler 0.22 "Catch 22"](https://blog.gitbutler.com/gitbutler-0-22), accessed 2026-09-24)
- **Description-based stacks** (fallback, when native isn't available/enrolled): GitButler's own instruction is _"merge from the bottom upward,"_ and it recommends enabling _"automatic branch deletion on GitHub so GitHub can retarget the next pull request after its base branch lands,"_ then running `but pull` locally to resync the workspace from the target branch. ([docs.gitbutler.com — Create stacked branches and pull requests](https://docs.gitbutler.com/features/branch-management/stacked-branches), accessed 2026-09-24)
- Neither the docs page nor the linked blog post contains an explicit "don't squash" warning in so many words — the closest thing to the "explicit warning" the question asked me to find is **not** a docs sentence but a **live, first-party bug report**: GitButler's own issue tracker shows the tool currently mishandles exactly the squash-merged-stack case (detailed in Mechanics above), which is the practical, primary-source-backed version of "GitButler warns about squash + stacking" — it's a known-bug admission rather than a docs warning. ([gitbutlerapp/gitbutler#15154](https://github.com/gitbutlerapp/gitbutler/issues/15154), accessed 2026-09-24)

**Graphite (graphite.dev / graphite.com).** Graphite's own guidance is the most direct "which merge method should stacks default to" statement found:

- _"Fast-moving teams in production environments should default to a stacking workflow that continually rebases into main. This integrates changes frequently in small increments while retaining authorship details."_ — i.e., Graphite's own recommended default for a stacking-heavy team is **rebase**, not squash, precisely because rebase preserves per-commit identity across the stack the way squash does not.
- Graphite also states the general-purpose case for squash directly causing stack pain: _"when a team uses a --squash merge strategy where each PR turns into a single commit when merged into main, this can create challenges because subsequent PRs that were branched off the old history will suddenly show all of the merged PR's commits too"_ — this is Graphite's own restatement of the phantom-diff mechanism, in the context of stacking specifically.
- Graphite's own CLI mitigates it directly: `gt squash`/restacking is described as ensuring "correct restacking" after a squash, i.e. Graphite's answer to "squash + stacks" is not "don't squash," it's "squash, then let the tool restack for you automatically." ([graphite.com/blog — What's the best GitHub pull request merge strategy?](https://graphite.com/blog/pull-request-merge-strategy), accessed 2026-09-24)

**Git Town** (a third independent stacked-branch tool, useful corroboration though not one of the three tools named in the brief): states the mechanism in the clearest single sentence found in this research — _"After shipping the oldest branch from a stack using a squash-merge, main contains a new commit with the same changes as the shipped branch but a different commit hash. When syncing, Git sees the new commit on main and the commit on the shipped branch as conflicting edits to the same line"_ — and its own recommendation is to **avoid squash for shipping stack layers and prefer fast-forward merges**, specifically because "fast-forwarding keeps commit history between your stack and main identical, avoiding synthetic differences that cause phantom conflicts." Where squash can't be avoided, Git Town's mitigation is the same restack-immediately pattern as Graphite's. ([git-town.com/stacked-changes.html](https://www.git-town.com/stacked-changes.html), accessed 2026-09-24)

**Sapling/ghstack (Meta).** Not independently verified in this pass — not fetched from a primary Meta/Sapling source; see Caveats. Community discussion generally describes ghstack's model as "one commit = one PR, always merged/landed individually with history rewritten by the tool," which sidesteps the N:1 squash-collapse problem by never having more than one commit per PR to begin with, but this characterization is from secondary sources only and is flagged accordingly.

## Sub-issues and stacked PRs: independent features

GitHub's sub-issues feature (issue hierarchies) and issue dependencies (`blocked_by`, used by this repo's wayfinder convention per `docs/agents/issue-tracker.md`) are documented entirely separately from stacked pull requests, with no cross-references found in either doc set. Sub-issues docs describe breaking a large issue into smaller linked issues; stacked-PR docs describe an ordered chain of _branches/PRs_. GitHub does not appear to auto-derive a PR stack from a sub-issue hierarchy, or vice versa — **this repo would be combining the two conventions itself** (one sub-issue per tracer-bullet ticket, one stacked PR per sub-issue), which is a reasonable manual pairing but not a built-in, GitHub-maintained linkage. ([docs.github.com — About issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues), accessed 2026-09-24; docs.github.com stacked-PR pages cited above, accessed 2026-09-24 — no mention of issues/sub-issues in either)

## Recommendation for ubeann/vmb specifically

Given this repo already: uses GitButler for stack management (`but move --above`, `but pr new -t`), uses GitHub sub-issues + `blocked_by` dependencies for the umbrella/tracer-bullet structure, and currently has `allow_squash_merge`, `allow_merge_commit`, and `allow_rebase_merge` all enabled with `delete_branch_on_merge: false` (checked live via `gh api repos/ubeann/vmb`, 2026-09-24):

1. **Enable "Automatically delete head branches"** regardless of the squash decision — it's the one concrete, low-risk config change every primary source (GitHub's stacked-PR docs, GitButler's docs) points to as necessary for clean retargeting of the next PR in a stack.
2. **Don't blanket-default to squash across all PRs.** Set squash as the default _merge button behavior_ if desired for convenience, but treat any PR that is the base of another open PR (i.e., has a child stacked on it) as an exception that should be merge-commit or rebase-merged instead — or merged together with its stack via one atomic action rather than left half-merged.
3. **Investigate whether the repo can enroll in GitHub's native stacked-PR public preview.** If available, this removes most of the risk described here: native stacks apply squash (or any method) per-layer as one atomic bottom-up operation with automatic retargeting, which is exactly the documented safe path. GitButler itself already defers to native stacks when the repo supports them (0.22+). This is worth a five-minute check before committing to a workaround-based policy.
4. **If staying on the current description-based (non-native) GitButler stacking**, adopt the Graphite/Git Town pattern explicitly: merge bottom-up, one layer at a time, and run `but pull` (or equivalent restack) _immediately_ after each merge before doing further work on the branches above — don't let a squash-merged bottom PR sit stale. Given the open GitButler bug (#15154) in this exact scenario, budget for occasionally needing a manual `git rebase --onto`/`but` intervention if GitButler's own auto-restack mis-detects the squash as unintegrated.
5. Update `docs/agents/git-workflow.md`'s "Merging" section once a decision is made — the current text ("Merge with `gh pr merge --merge`... history so far preserves each PR's own commit(s)") should be revised to state the new default and the stacked-PR exception explicitly, so future agents don't squash a PR with children stacked on it by default.
