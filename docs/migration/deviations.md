# Deviation ledger

Every intentional difference between the new VMB schema and the legacy `vmb-warehouse` schema lives here — what changed, why, and what carries it. `CONTEXT.md` is the glossary; `docs/adr/` holds the decisions; this is the itemized register.

Source of truth for the legacy shape: `docs/research/legacy-schema-inventory.md`.

## Status key

- **decided** — settled; the carrying migration or ticket exists or is scheduled.
- **deferred** — knowingly differs from legacy, but the change lands later (usually a semantic change over loaded data).
- **open** — needs a business or design input before it can be carried.

### Not schema, so nothing migrates

The inventory also found defects in the legacy **application**: the missing `payment_proof_url` / `receipt_proof_url` accessors, a `StockRequisitionStatus` class that does not exist, phantom `$fillable` entries (`bill_id`, trip fee columns), an erroneous `down()` in a Laravel migration, and a Filament filter carrying a third status vocabulary. None of these are database shape, and the new code does not inherit them, so there is no migration to write.

### Deferred, with the reason

- **`master.users.remember_token`** — dropped once Better Auth's session semantics replace it, which is #7's work rather than a schema fix.

### A risk worth knowing about M-002 and M-006

`SET NOT NULL` and `ADD CONSTRAINT ... UNIQUE` validate the rows that are already there. On a snapshot whose data violates them — a Division with no code, two approvals for the same target and level, two requests sharing a quotation, two locations sharing a code, two plan rows sharing a trip and code — the migration fails and the import reports which statement. That is deliberate, and it is why rows M-002, M-006, M-009, M-013, M-015, M-017, M-018, M-019 and M-020 all carry it; the alternative is a constraint that silently does not hold. Note the asymmetry M-014 and M-015 show: correcting a _default_ only affects rows written afterwards, so a snapshot whose rows already carry the old value fails the check that follows. That is the pipeline working: the alternative is a constraint that silently does not hold. If a real snapshot trips one, the answer is a data decision recorded here, not a quiet `NOT VALID`.

## S. Semantic register

Changes in meaning or model. Deferred to migrations over loaded data.

**Database-wide**

- Timestamps become `timestamptz(3)` (`0022`). Every legacy column was a wall-clock in Asia/Jakarta and is converted with `AT TIME ZONE 'Asia/Jakarta'` in the `USING` clause, never through the session's zone; Better Auth's tables were written by the application through the driver, which serialises a `Date` as UTC and lands it in a session that is also UTC — so they use `'UTC'`. That reasoning is sound but untested against a real row: a row written from a non-UTC process would be seven hours out, and nothing in the data could reveal it. On the legacy side the assumption is the confirmed one — all production data is WIB — and a row written in another zone would be silently misinterpreted, with nothing in the data to reveal it. The pipeline reports the instants it could not reconcile, but only for the columns a snapshot carries. The pipeline's verifier now compares timestamps as **instants** (`instant`), so a parity check does not report a seven-hour drift. Storage is UTC from here on: `timestamptz` holds an absolute instant, and a zone is applied only to interpret a literal on the way in or to render one on the way out. Rendering uses the reader's own zone, which their profile carries (#115) — never the server's.

**Trucking**

- Replace `invoice_shipments.order_number` string with a real order FK; add an explicit invoice→order/trip relation.
- Normalise DTP/DTA `route_reference` and `changed_routes` (today a JSON override next to a real FK on `trips`).
- Decide whether trip `routes` JSON snapshots stay denormalised or normalise to trip-route-locations.
- Reconcile cancellation semantics and the `orders.code` integer business key.

**Warehouse**

- Model rejection explicitly — `REJECTED` is currently unreachable and no reject action exists.
- Replace denormalised `current_stock` with a stock-movement ledger.
- Split quotation/payment/receipt into event rows; give stock alerts a lifecycle and dedupe.

**Expense**

- Decide class-table inheritance vs collapsing shared evidence columns onto `requests`.
- Decide whether a budget is a single mutable allowance or per-period (`budget_month`).
- Decide whether a request's `amount` is stored or derived, and stop exposing it as a sortable SQL column either way.
- Extract file references — the per-variant JSON columns and paths — into one documents table.
- Decide whether monthly budget spend is materialised or stays a runtime sum.
- Drop the polymorphic approval columns if only expense requests are ever approved.
- Retention and soft-delete policy for financial records.

**Identity / RBAC**

- Export the Spatie role→permission matrix and role assignments before dropping; Filament-Shield's configured role name (`super_admin`) does not match the seeded role (`Super Admin`) — a landmine for the mapper.
- `master.users` outlives the transform as the business record (ADR-0032): credentials, sessions and email verification move to Better Auth, the legacy `password` and `remember_token` columns drop, and `email_verified_at` maps to `emailVerified`. No `active`/`inactive`/`suspended` status is carried into any gate — the unmerged `origin/refactor/divisions-on-roles` branch removes the column, and VMB is not inventing an active/deactivated concept now.
- Passwords are not migrated (ADR-0033): every migrated account activates once by email OTP, proving inbox control and setting a new password; the bcrypt hashes stay in the raw snapshot only.
- Multi-division membership follows the legacy refactor direction onto roles — an input to #8 (BC-001); profile stays on `master.users`, with timezone/locale preferences on Better Auth's user via `additionalFields` (#115, BC-002).

## Verification of deviations

Parity is proven per import and at cutover by: per-table row counts, checksums over business keys per domain, FK integrity across the preserved legacy UUIDs, and a documented per-domain spot-check list (#18).
